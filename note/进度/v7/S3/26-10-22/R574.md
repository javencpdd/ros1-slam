## 一、本条要解决的是什么

批225 交出去的时候，门禁串的读数里有两处「说不清」：一是整串跑不完，二是三件在串内恒红而单跑全绿。这两处留着，等于门禁串本身不可信——**一个只在串里红的闸，和没有闸是一样的**。本批把两条一次查到底，结论是：**一条是我自己的观测错，一条是真缺陷但不在判据里、在传参上。**

## 二、假缺口：整串「只写 4 行就死」

### 现象
把 `bash scripts/verify/run_gate_chain.sh > 文件 2>&1` 放后台跑，文件永远只有 4 行（三行表头 + 第一件）。前台跑被 SIGTERM；`setsid nohup` 起也一样。批225 据此登记了「整串未能成串，交下批判真假」。

### 定位过程
1. `bash -x` 加 `timeout`，把 stderr 重定向到管道再看：发现 `read` 循环正常逐行跳过注释，然后**依次打印了 SYN rc=0、GTC rc=5、ISO rc=1…**——它根本不是跑 4 行就死，是一直在往下跑。
2. 差别在哪：`bash -x` 那次是 `2>&1 | head`（管道），而失败那次是 `> 文件`。**管道按行刷新、文件按块刷新。**
3. 于是判定：stdout 接文件时是块缓冲（4KB），前 4 行（约 400 字节）一直在缓冲区里没刷出去；SIGTERM 一到，缓冲区整段丢弃 ⇒ 文件里看着"只写了 4 行"，而进程其实已经跑到第 5、6 件了。

### 结论
★不是运行器缺陷、不是某件挂住、不是后台被截断——是我的观测方式把块缓冲丢了的那部分读成了「早死」。★
正形＝判「是否早死」之前先换行缓冲重跑一次（`stdbuf -oL -eL`），或者干脆看进程还在不在（`ps`）而不是看文件行数。

## 四、修法：只补口，不改义

### 三个件各加一行
```bash
# GTC
ROOT="${GTC_ROOT:-/home/ros1-slam}"
# VAR
ROOT="${VAR_ROOT:-/home/ros1-slam}"
cd "$ROOT" || { echo "[前置缺失] 仓根不可达：$ROOT（可用 VAR_ROOT=仓根 覆写）"; echo "VAR VERDICT rc=9"; exit 9; }
# DC
ROOT="${DC_ROOT:-/home/ros1-slam}"
```
关键约束（写进注释了）：
- **缺省值一字不改**（仍 `/home/ros1-slam`）⇒ 在开发机上行为零变化，不是"迁就本仓而改默认"。
- **rc 语义一字不改**：GTC 仍 0／5，VAR 仍 0／5／9，DC 仍 0／1／5／9。
- VAR 额外补一条前置缺失自报警（根不可达时提示可用 `VAR_ROOT` 覆写），与 VCC 的 R407 根自检同风格。

### 运行器补四支
```bash
GTC)   ( cd "$ROOT" && GTC_ROOT="$ROOT" bash "$path" ) > "$out" 2>&1 ;;
VAR)   ( cd "$ROOT" && VAR_ROOT="$ROOT" bash "$path" $(grep -vE '^ *(#|$)' scripts/verify/claim_face.txt) ) > "$out" 2>&1 ;;
DC)    ( cd "$ROOT" && DC_ROOT="$ROOT" bash "$path" ) > "$out" 2>&1 ;;
账构)  ( cd "$ROOT" && VLB_ROOT="$ROOT" bash "$path" ) > "$out" 2>&1 ;;
```
与既有 `VCC)` 支**同一写法、同一理由**。VCC 支的原注释已经把「件内缺省根在异机是符号链接视图 ⇒ 必须传根」写清了，本批是它的同族扩面，不是新决策。

> 纪律说明：本批**没有**把这三件的黑名单式修法写进形检或新增闸去「防止再犯」。理由是——防再犯的正形是「凡件内出现绝对路径仓根即报警」，那是判据面变更，须先落笔验收（05 A3）。本批只修事实，不顺手造闸。

## 六、VAR 在本机不可判（★这一条最容易被读错★）

补根后 VAR 不再报路径错，改成报探针不过：
```
[FAIL] P1b 阳性对照·不可达侧：600＋同条目但 mask::--- ⇒ 算法须判不可读：实得=None
VAR VERDICT rc=9（P1 未过＝探针无分辨力，普查结果一律不采信）
```

### 查到底
1. 先怀疑算法。读 `readable()`：第 139 行有 `if st.st_uid == uid` 守卫 —— owner 位只在「查询者就是 owner」时才短路，而 P1b 夹具 owner 是 root、查询者是 ros1-slam ⇒ **不该走 owner 分支，算法没错**。
2. 再怀疑 setfacl。手复现：
   ```
   setfacl -m u:ros1-slam:rw- b.txt   → setfacl: 选项 -m: 无效的参数 靠近字符 3（rc=2）
   setfacl -m m::--- b.txt            → rc=0（这个能过）
   id ros1-slam                       → id: "ros1-slam": 无此用户
   ```
   即：**本沙箱里根本没有 ros1-slam 这个用户**，具名 ACL 条目建不出来；`pwd.getpwnam('ros1-slam')` 抛 KeyError ⇒ `readable()` 返回 `None` ⇒ `r_bad is False` 不成立 ⇒ P1b 必然不过。

### 定性
★VAR 的 rc=9 在本机是**环境性不可判**。不得读成「件坏了」，也不得读成「仓里权限没问题」——它是**没判**。★
这与坑17 的无 sudo 路径同源（本仓一直没有真正的协作账号），不是本批修复引入的新缺陷。
**处置＝只登记、不改探针**。改探针的账号解析属判据面变更，须先落笔验收。

## 八、本批自曝与教训

1. **把块缓冲丢掉的部分读成「进程早死」**——这是本批最大的自我纠错。批225 已经把它记成「未归因项」，本批推翻。教训写进 05：判早死先看进程、再看文件；要看文件就先 `stdbuf -oL -eL`。
2. **「看起来像环境没配好」的红，最容易被当噪声挂起来**。四件的恒红挂了两批，根因是一行绝对路径。教训：`cd: <绝对路径>: 没有那个文件或目录` 这类输出，第一反应应当是「这个件把路径写死了」，而不是「环境没配」。
3. **`mkdir -p` 与后台命令写在同一行时会丢**。本批第一次启动后台时 `mkdir -p ~/.cache/r574 && ... &` 整条没生效（目录不存在、文件写不出），拆成两条即正常。记在这里：**建目录与起后台任务不要合成一条**。
4. **对照组的价值**。找根因时真正救场的是 `v_citation_check.sh` 那一个「同族但是对的」件——没有它，很容易得出「这些件就是这么设计的」这种错误结论。
