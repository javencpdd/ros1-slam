## 三、h 的语义（自此由我方持有）

### 3.1 定义（逐字）

> **h ＝ 相对局部地面的离地高，单位：米·正上。**
> 亦即 `h = z_点 − z_局部地面`，同一格里逐点取 h 的最大值。**地面本身 h ≡ 0。**

### 3.2 与合并层 yaml 逐项对表（写死，改任一条都要回 04 登记）

| 项 | 消费侧（`config/elevation_merged_layer.yaml`） | 生产侧（本节点缺省参数） | 是否逐字一致 |
|---|---|---|---|
| 层名 | `layer_name: elevation` | `~layer_name: "elevation"` | ✅ 一致 |
| 分辨率 | `resolution: 0.1`（基键） | `~grid_resolution: 0.1` | ✅ 一致 |
| 话题 | `input_topic: /elevation_mapping/elevation_map` | `~output_topic: /elevation_mapping/elevation_map` | ✅ 一致 |
| 判据 | `h > ground_z + height_threshold`（`0.0 + 0.15`） | 生产侧**不设判据**（判据归消费侧） | — 刻意如此 |
| 帧 | `global_frame: map` | `~grid_frame: map`（不可达时按候选序退） | ⚠ 见 §4 差异 |

### 3.3 附带收益（用户明写要求写进设计件）

**R569 §三 优化一那个「h 语义取决于生产者」的不确定，自此消失**——因为我们自己就是生产者。上游 `elevation_mapping` 若发绝对高度，h 的零点就随雷达架高漂；若发离地高，零点固定。本节点取后者，且零点由「局部地面分位」现算，**与雷达架高、下倾角、机器人俯仰全部解耦**。

### 3.4 局部地面怎么求（可被证伪的那种做法）

滚动窗内取**近地分位**：落在竖窗 `[ground_z_min, ground_z_max]`（缺省 `[-2.0, 0.5]`）内的点按 z 排序，取第 `ground_percentile` 分位（缺省 **20%**）。

- **为什么是分位不是最小值**：最小值对单点噪声、对地面上的小台阶极敏感；分位对"窗里台阶占了 x%"这种构图变化不敏感，平地时收敛到真地面。
- **为什么是 20% 不是 50%**：上楼梯时地平面上方开始有点（第一级台面），分位越低越贴真地面；但太低（如 1%）会被地面噪点往下拽。20% 在本仓仿真点云下平地与梯脚都能读出正确地面（自测 T1／T5／T6 实证）。

## 四、★本批发现并修掉的两个真缺陷（都不是"调参"，是错）★

### 缺陷 A：未命中填充点被当成地面 ⇒ ground_z 抬到雷达安装高

**症状**：第一版跑真实仿真，读数 `ground_z=0.450`（真地面是 0）、`h_max=0.000`、有效格只剩 308。

**根因（盘上铁证）**：`livox_laser_simulation` 对**射线未命中**填充 `(0,0,0)`（不是 NaN）。20000 点里 **16675 点 range=0**（83%），经 tf 变到 odom 后恰好全部落在 z=0.45＝`MID360_MOUNT_Z` 那一层。于是：
1. 地面分位法把它们当成地面 ⇒ `ground_z` 读出 0.45；
2. `h = z − 0.45` ⇒ 整片地面被判成 −0.45，台阶也压到 0 以下 ⇒ `h_max=0`。

**这段最危险的地方**：它长得像"链路通但算法没效果"，极易被误判成栅格化写错了。

**修法**：`drop_invalid_points()`，在**求地面之前**按 range 剔（缺省 `min_range=0.20`）。顺序不可换——放到后面就晚了。

### 缺陷 B：`np.maximum.at` 铺在 NaN 初值上，整片仍是 NaN

**症状**：自测 T2 直接 `ValueError: zero-size array`，有效格 0。

**根因**：`np.maximum.at(acc, ...)` 里 NaN 参与 maximum 结果仍是 NaN（本机 Python 3.13／numpy 实核，且抛 `invalid value encountered in maximum`）。

**修法**：先用 `-inf` 铺底做逐格取大，再把**从未被写到**的格显式改回 NaN。★"无点 ≠ 高 0"★——不显式处理，消费侧会把真空格当平地放行。

### 另有两条实现坑（记下来防再踩）

- **点云解码不能写成 `buf[idx:idx+4]`**：切片窗口长度恒定 ⇒ numpy 降维，抛 `only integer scalar arrays can be converted to a scalar index`。正解＝`reshape(n, point_step)` 后按列取偏移。
- **`pkill -f <脚本名>` 会杀掉自己所在的 bash 命令行**（匹配串命中自身）⇒ 必须按 PID 或写脚本文件。本批实测两次。

### 5.4 帧差异（★必须呈报，不是我能自裁的★）

消费侧 `costmap_common.yaml` 的 `global_frame` 是 **`map`**，但**仿真台上 `map→odom` 段只在 m2_teb 链路里由 `m2_tf_fresh` 提供**；`stairstudy`／`m1_gazebo` 这些台子上根本没有 `map` 帧（tf 树实测只有 `odom→base_link→rslidar`）。硬取 `map` ⇒ 本节点在那些台子上永远 INVALID。

**现行处置**：按 `frame_candidates` 顺序**探第一个能查到的祖先帧**（缺省 `[map, odom, base_link]`），把**实际用的那个帧**写进 GridMap 头。消费侧 `ElevationMergedLayer` 本来就会对"帧 ≠ 全局帧"做 tf 平面变换（`updateBounds` 里 `map.getFrameId() != global_frame` 分支），所以换成 `odom` 不改变其语义，只是少绕一层 `map→odom` 恒等变换。

**待真人定**：挂载实验时是否一律补一条 `map→odom` 恒等桥（与 m2_teb 同式），让 GridMap 恒定在 `map` 帧？——本批**未自裁**，两种跑法都能验 h 语义，但账上口径不同。
