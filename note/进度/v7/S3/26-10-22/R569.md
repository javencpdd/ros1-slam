## 三、本地方案的优化建议（按优先级）

### 优化零（★比下面三条都前置：链路根本没有生产者★）

**这是查证过程中发现的、比参数语义更硬的一条阻塞。**

`elevation_merged_layer.yaml` 的输入是：

```
input_topic: /elevation_mapping/elevation_map   # grid_map_msgs/GridMap
```

但全仓现查：

| 检查 | 结果 |
|---|---|
| `grep -rn "elevation_map" ws/src --include=*.launch --include=*.yaml`（排除合并层自身） | **零命中** |
| 唯一带 `grid_map` 依赖的包 `30_perception/deeprobotics_local_height_map` | **带 `CATKIN_IGNORE`（空文件）＝被 catkin 跳过、不参与编译、不产生任何节点** |

**含义**：合并层挂进 costmap 之后，它会**永远收不到一份 GridMap**。验收标准里的第三行日志「Received a grid map」**不可能出现**。此时若只按「Using plugin 行／在位行」两行判活，会得到一个**看起来装上了、实际永远不写格的假活**。

★这正是本仓反复吃的那个坑的形状★（「闸门自己闭上眼」：检查项通过了，但被检查的东西根本没在跑）。所以**优化零＝在挂载之前先解决生产者**，否则挂载动作本身没有验证意义。

**三条出路**（需真人定，本侧不代选）：

| 案 | 做法 | 代价 |
|---|---|---|
| 甲 | 解 `CATKIN_IGNORE`，编译 `deeprobotics_local_height_map`，接它作为生产者 | 要判该包与现役 STVL 是否冲突、以及它自身是否可编（依赖闭包未核） |
| 乙 | 引入 `elevation_mapping`（ANYbotics，外部方案里的通用选择）作为生产者 | 新第三方包入仓，与「第三方原样复制」红线打交道 |
| 丙 | 自己写一个最小生产者（从 `/rslidar_points` 直接算 2.5D 高程，滚动窗口） | 要写算法，落入壳包红线讨论面 |

★施工侧倾向：先做**甲的前置判定**——只判「该包能不能编、编了会不会与 STVII/sob_layer 冲突」，这一步不改任何在册件、只出结论★。

### 优化一（★重要★）：高程合并层的 `ground_z` 是固定值，爬梯时会整段误判为障碍

> ★本条以下为**推断，未经实测**★：`h` 的语义取决于生产者输出（见优化零）。若生产者是 `elevation_mapping` 那一族，`h` 是**离地高度**；若是自算的点云 z 差，则可能是**世界系绝对高**。**语义未定前，下面对 `ground_z` 的批评只能是候选假设，不能当结论用**。

**症状**：`src/elevation_merged_layer.cpp:149` 判据为

```
h <= ground_z_ + height_threshold_  ⇒  视为可通行（不写障碍）
```

而 `ground_z` 在 yaml 里是**固定常数 0.0**，`height_threshold` 固定 0.15。

**为什么这是结构性问题**：`grid_map` 的高程 `h` 是**相对地面高度**（elevation_mapping 输出的正是离地高度），不是世界系绝对高度。但在**楼梯上**，机器人脚下地面本身已在上升——此时如果 `h` 仍是「离地高」，那么判据本身是自洽的；**但如果合并层把 `h` 当作世界 z 来解释（`ground_z: 0.0` 这个默认值暗示了这种读法），那么走上第二级台阶后，整段台阶面的 `h` 都会 > 0.15，被整片标成 254 致命障碍**，机器人会认为「前方全是墙」。

**这正是 RAEM 那篇点出的同类失效**：严格可通行性过滤器在楼梯上会失效，因为「地面」这个概念在 3D 结构里不再是全局常量。RAEM 的处置是**分层**：全局用稀疏拓扑、局部用更宽松的栅格兜底，并显式区分「可通行」与「占用」两个态。

**建议（三选，需真人定）**：

| 案 | 做法 | 代价 |
|---|---|---|
| 甲 | 明确 `h` 语义＝**离地高度**（elevation_mapping 原生口径），`ground_z` 恒 0 是对的，但**必须在代码注释与 yaml 里写死这条语义**，并在爬梯窗实测验证 | 只加注释与一次验证，最小改动 |
| 乙 | 引入**局部地面基准**：用机器人脚下窗口的 `h` 中位数（或低分位数）作为滚动 `ground_z`，判据改为「相对局部地面的高差」 | 要改算法；且楼梯上行时「脚下地面」本身在变，需正反控 |
| 丙 | 只把该层用于**平地+坡道**，楼梯段显式关层（`enabled: false`），楼梯交给全局层析方案 | 保守；放弃该层在楼梯上的作用，但换来语义干净 |

★施工侧倾向：先做甲（一次实测就能定性），若实测证伪再上乙★。甲的价值在于它**只用一次仿真窗就能证伪**——这正是当前最缺的东西。

### 优化二：全局规划器是纯 2D，多楼层/爬梯场景结构上无解

NavFn 在 2D 栅格上搜，**搜索空间没有 z**。所以无论你把高程层写得多好，它最多只能告诉你「这一格代价高」，不能给你「从一层走到二层」的路径——因为二层和一层在 2D 栅格里是**同一批格子**。

**这正是 PCT 层析存在的理由**：把 3D 压成「等距水平切片堆」，每个切片记 `elev_g`（地面高）与 `elev_c`（天花板高），A\* 在切片间通过「门（gateway）」跳层。它与你的 SCAN-Planner 是同一族。

**建议**：把 PCT 作为**全局层的第二实现**并列接入（不改现有 NavFn，做可切换），用 `legbot_3D_Nav` 的接口形状做参照——它的链路是 `PCD → PCT tomogram → 多层 A* → /pct_path → 局部规划`。**接口成本低**：PCT 输出 `nav_msgs/Path`，与现有 `move_base`/`mbf` 的全局路径消费面同形。

**但要诚实说清代价**（外部方案自己承认的两条）：
1. **假设世界静态**、且**依赖高质量离线点云**。⇒ 你的 `stairstudy` 恰好已经在把「点云质量」当自变量扫（分辨率 0.05/0.10/0.15/0.30、安装高、俯仰），这块资产**正好可以复用来喂 PCT 的输入前提**。
2. 需要 CUDA（`CuPy`）。你的容器里有没有 CUDA 是**未核**项，须先判。

### 优化三：TEB 在阶梯上的适配是隐藏风险

外部 `3d_dog_navi_ros2` 给了一个很实用的细节：**pitch > 15° 自动切「轮腿协同」模式**。这不是花招，而是承认「上坡时腿式与轮式的最优策略不同」。

你现役是 TEB。TEB 的轨迹模型是**差速/全向的 2D 运动学**，它把机器人当平面刚体。在**台阶**上，「平面刚体」假设会在两处失守：
- 台阶前沿是**离散高程跳变**，TEB 的平滑代价函数会把它当「可绕过的障碍」而不是「需要抬腿的地形」；
- 楼梯上行时质心前倾，TEB 的速度指令可能给出**超过腿部步态能力的加减速**。

**建议**：**不要在楼梯上直接用 TEB 的参数默认值**。最小可行做法＝在阶梯世界件上扫 `max_vel_x` 与 `acc_lim_x` 两枚，得到「步态能吃下的速度带」；这与你在 `stairstudy` 里「距离窗 / 高度带」的扫法完全同族——**同一套方法论，换一个自变量**。

## 四、外部方案给不了什么（要诚实标注）

1. **它不解决你的「判据/门值」问题**。外部那些读数（成功率、末端误差）都是在他们自己的机器人、自己的世界件上取得的，**不能当你的门值**。任何拿来即用的阈值都是伪造。
2. **legbot 的末端 Z 误差 0.38 m 是个警号**：它两套局部规划器（EGO 与 SCAN）的末端 3D 误差分别 0.397 m 与 0.392 m，其中 Z 向都占 0.38 m 量级。说明「3D 规划跑通」与「落脚高度对」是两件事，**你的判据必须把 Z 单独设一项**，不能被「到达成功」掩盖。
3. **它没有 Gazebo 物理可信度的处置**。外部方案全都没谈脚部摩擦与接触刚度。而你上一轮已查到的数字（`mu1/mu2 = 0.6~1.0`、`kp 1e6~1e7`、`kd 10~100`，以及 CHAMP 官方世界用 `mu=100/mu2=50` 这种夸张值换抓地力）说明：**摩擦力不扫，「能上楼梯」这个结论不可迁移到真机**。
