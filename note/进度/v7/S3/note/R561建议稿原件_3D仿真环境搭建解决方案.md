## 一、结论速览

R560 的五面二十项，按「是否需要先解一条观测口径」可以重排成三类，这比按 G/W/J/S 分面更能决定施工顺序：

| 类别 | 条目 | 性质 | 是否需要授权 |
|---|---|---|---|
| **甲·口径未闭，施工会白做** | G2、G5、W3、W4、J2 | 观测量的定义或基准不唯一 | 否（只读、只新增脚本） |
| **乙·缺陷已定位，可当场修** | W2、W1、S3 | 实现缺陷／引用悬空 | 否（缺陷修复，不触参数） |
| **丙·须新建，各自有主** | G1、G3、S1、S2、J1、J3、J4、J5 | 需新件或需定标 | 部分是（Q1—Q4） |

由此得到三条主结论：

1. **规划栈选型不受任何闸门限制，应立刻定下来。** 项目侧是 ROS1 Noetic（`mesh_navigation` noetic 分支两试两败、`TerrainPlanner` 不在 noetic 分支）。因此在 Noetic 上做 3D 全局／局部规划，必须走 `move_base` + `costmap_2d` 插件体系，或用 `move_base_flex`（MBF）替代 `move_base`。**不要指望把 ROS2 Nav2 的方案平移过来**——Nav2 的 `nav2_costmap_3d` 在 Noetic 上不存在。
2. **G5 与 W3 可以判掉，而不是继续并报。** `ring` 是发布侧写入的标签，恒 32/32，世界件空载时同样 32，故它不反映射线集；在册「±15.5° 带内约 8 条」是 T8 解析臂按 `100×50` 名义栅格算出的模型产物。**两边都不是测量**，32 与 8 的争执是两个模型之争。口径应换成「每帧束数 + zenith 占用箱数（带分箱粒度）」。
3. **真正挡住工程面的是两条，不是二十条。** 一条是 W2（世界件静默不加载 → 一切读数都可能是假读数），一条是 G2/J2（雷达离地高度 `h` 未定标 → `R_min` 有 3.44—4.66 m 的 20%+ 摆幅，而 `R_min` 是「近场补不上」这个结论的唯一支撑）。**这两条不闭，任何近场判据都在浮沙上。**

## 二、总体架构：三层解耦

### 2.1 分层与职责

R560 里 G3「机体无腿」之所以成为阻塞，根因是**一个刚体盒试图同时承担导航判据与步态判据**。解法不是补腿，而是拆层：

```
┌──────────────────────────────────────────────────────────────┐
│ L3 规划层（本件主战场）                                        │
│   全局：global_planner / navfn / 自研 OMPL 采样（SE2+高程）    │
│   局部：teb_local_planner / dwa / mpc_local_planner            │
│   二者只吃 costmap，不关心腿长什么样                            │
├──────────────────────────────────────────────────────────────┤
│ L2 环境表示层（需新建，S1/S2 的正解）                           │
│   elevation 栅格（grid_map）→ 地形特征（坡度/台阶/粗糙度）      │
│   → costmap_2d 自定义 layer（键挂 elevation/ 前缀）             │
├──────────────────────────────────────────────────────────────┤
│ L1 载体层（拆两件，G3 的正解）                                  │
│   载体 A「导航态」：刚体盒 + IMU + lidar   ← 承载 L3 全部判据    │
│   载体 B「步态态」：12 关节 + 足端接触     ← 只承载步态判据      │
├──────────────────────────────────────────────────────────────┤
│ L0 世界层（W1/W2 的正解）                                      │
│   stair_lab 八枚世界件 + 空白对照景（G1 正解）                   │
└──────────────────────────────────────────────────────────────┘
```

**关键设计判断**：L3 规划层对 L1 的形态**无感知**。全局规划器输入是 costmap、输出是 `nav_msgs/Path`；局部规划器输入是 costmap + `odom` + `Path`、输出是 `geometry_msgs/Twist`。只要载体 A 能发布 `/odom`、能接受 `/cmd_vel`，规划判据就能全跑，**完全不必等腿**。这直接把 G3 从「阻塞全批」降级为「只阻塞步态判据子集」。

### 2.2 数据流（导航态最小闭环）

```
[世界件] --gzserver--> /clock, /gazebo/model_states
                              │
                    ┌─────────┴──────────┐
                    │                    │
              [lidar 插件]         [world_load_assert]  ← 新增（A 项）
                    │                    │ fail → 零退出，不开录
              /livox/lidar (PointCloud2)
                    │
        ┌───────────┴────────────┐
   在线建图                    离线切片（B 项：冻 bag）
   (LIO/SLAM)                      │
        │                    同一条 bag 反复重跑
   /map + TF(map→odom→base)        │
        │                          │
   ┌────┴──────────────┐      [elevation 离线重建]
   │                   │           │
[grid_map 高程层]  [AMCL/定位]      └→ lvr2 真值网格（离线评估基准）
   │                   │
[elevation costmap layer]（新增，S1/S2 正解）
   │
   ├→ global_costmap → global_planner → /plan (nav_msgs/Path)
   └→ local_costmap  → teb/dwa        → /cmd_vel
                                            │
                                     [载体 A 差速/全向插件]
```

### 2.3 坐标系与话题契约（建议固定，避免后续漂移）

| 项 | 建议符号 | 说明 |
|---|---|---|
| 地图系 | `map` | SLAM 输出 |
| 里程计系 | `odom` | LIO 输出 |
| 机体水平投影 | `base_footprint` | **所有路面高度读数的参考原点** |
| 雷达系 | `livox_frame` | 其相对 `base_footprint` 的 `translation.z` ＝ 本件反复要求的 `h` |
| 高程层键前缀 | `elevation/` | 强制，禁裸 `resolution`／`slope`／`step`（合 S2 要求） |
| 高程栅格话题 | `/elevation_grid` | 按 R347 窄义读（单层高程栅格不构成违令） |

> **`h` 的定标命令**（一次即可定案，建议列入 Wave 0）：
> `rosrun tf tf_echo base_footprint livox_frame`，站立态，取 `translation.z` 绝对值，同时记录 `(h, θ, 站立态)` 三元组——这正好满足 J2 要求的「任何 z 窗引用须连带安装位与站立态」。

## 三、规划栈方案（本件核心）

### 3.1 环境表示选型：为什么不能直接用 mesh_navigation

| 方案 | Noetic 可用性 | 3D 全局 | 3D 局部 | 结论 |
|---|---|---|---|---|
| `mesh_navigation` + MBF | ★两试两败（在册） | 理论最优（真 3D mesh） | 有 | **不作为主线**，仅保留为「若依赖修复则升级」的后备 |
| `TerrainPlanner` | 不在 noetic 分支 | — | — | 不可用 |
| **`grid_map` + 自写 costmap layer** | 官方 Noetic 发布 | ✔（2.5D 高程代价） | ✔ | **主线** |
| `octomap_server` + 3D 投影 | Noetic 原生 | 部分（占据→2D） | ✔ | 作补充层 |
| 自研 OMPL SE2+高程采样 | `ompl` 有 Noetic 包 | ✔（可在高度上搜索） | — | 全局备选，需求「跨层」时启用 |
| 纯 `costmap_2d` + 静态层 | 原生 | ✘（丢地形） | ✔ | 只作 2D 回归对照 |

**判断**：主线应是 **`grid_map` 承担高程表示 + 自写 `costmap_2d` 插件层承担地形→代价映射**。理由有三：第一，`grid_map` 在 Noetic 上有官方二进制包，不进入依赖泥潭；第二，自写插件层正好满足 S2「须新写 3D 面件、键挂 `elevation/` 前缀、不复活已搁置 2.5D 留盘件」；第三，它把 `lvr2` 从「编译失败的包袱」变成「离线真值资产」——而你最早问的 `opt/upstream/lvr2` 的作用，答案正好落在这里（`mesh_navigation` 的外部依赖明确含 LVR2 for mesh processing）。

> 附带一条对 S1 的技术判断：`mesh_navigation` 两试两败，**大概率不是它本身的问题，而是 `lvr2` 那一层**（Noetic ＝ Ubuntu 20.04，PCL 1.10 / FLANN 1.9 的 API 变动、Boost 1.71、C++14 与 C++17 混编，这几处最容易一起炸）。若要走后备路线，先单独把 `opt/upstream/lvr2` 编过再谈。这条不构成本批动作，只作为后续一轮的省时判断。

### 3.2 3D 全局规划方案

#### 3.2.1 主方案：2.5D 高程代价 + 平面搜索

| 环节 | 选型 | 职责 |
|---|---|---|
| 高程来源 | `grid_map`（在线）/ `elevation_mapping` 系（若需增量融合） | 存 `z`、`var`、坡度、粗糙度 |
| 地形特征 | `grid_map_filters`：`SlopeFilter`、`NormalVectorsFilter`、`ThresholdFilter`、`MeanInRadiusFilter` | 出坡度图、法向图、粗糙度图 |
| 代价合成 | **自研 layer**（见 3.4） | 坡度→代价、台阶→致命、未知→保守 |
| 全局搜索 | `global_planner/GlobalPlanner`（`use_dijkstra: false` ＝ A\*）或 `navfn/NavfnROS` | 出 `nav_msgs/Path` |

**这条路线严格说是 2.5D 而非真 3D**：路径在平面 `(x, y)` 上搜索，高度只以「代价」形式进入，路径本身不带 `z` 变化。对「机械狗在起伏地形上走到目标点」这类任务，这是正确且足够的抽象——因为狗的姿态由 L1 的 locomotion 决定，规划器不该管机身怎么倾斜。

#### 3.2.2 备选方案：真 3D 采样（仅当需求包含「跨层／跨越」时启用）

当判据要求在高度上连续变化（下层到上层、跨越沟壑上方、进入管道），2.5D 表达在数学上就不够。此时用 `ompl` 在 SE2 状态空间上叠高程代价：

```
StateSpace  : ob::SE2StateSpace（x, y, yaw）
ValidityChecker:
    z(x,y) = elevation.at('elevation')   // 双线性插值
    if z > z_prev + k_up   -> invalid    // 上坡超限
    if z < z_prev - k_down -> invalid    // 下坡超限
    if slope(x,y) > s_max  -> invalid    // 坡度超限（值待定标，J1）
    if step(x,y)  > h_max  -> invalid    // 台阶超限（值待定标，J1）
    if unknown(x,y)        -> invalid    // 未知区禁入
Optimizer   : RRT*  → PathSimplifier
```

★注意***：上式的 `k_up / k_down / s_max / h_max` 全部是**待定标占位符**，本件不给值（J1）。

#### 3.2.3 全局规划的验收形状（形状，非门值）

| 判据形状 | 正控（必须通过） | 反控（必须失败） |
|---|---|---|
| 到达 | 起点/终点均在自由区，路径连续无跳变 | 终点置于致命格 → 必须规划失败 |
| 地形合规 | 路径逐点坡度/台阶不超过（待定标）上限 | 直线穿过台阶立面 → 必须失败 |
| 未知区处理 | 路径不进入 `unknown`（或按策略显式标注） | 世界件空载（无地形）时行为可解释 |
| 最优性 | 同一起终点重复 N 次，路径长度方差在阈值内 | 人为加一堵墙 → 路径必须绕行 |

### 3.3 3D 局部规划方案

| 环节 | 选型 | 适合场景 | 注意 |
|---|---|---|---|
| 局部规划器 | `teb_local_planner` | 差速/全向，可带 footprint、可加 `via_points` | 四足转向需调 `min_vel_theta`，否则原地摆头 |
| 局部规划器 | `dwa_local_planner` | 最稳、参数少 | 无地形语义，只吃 costmap |
| 局部规划器 | `mpc_local_planner`（`mpc_local_planner` 包） | 需要动力学约束时 | Noetic 有包，配置成本高 |
| 局部代价层 | `voxel_layer` / `obstacle_layer` / 自研 `elevation` 层 | 见下 | **性能换精度**，见下 |

**局部层的取舍（这是实践中最容易踩的一条）**：

- `voxel_layer` 内部维护三维体素，做三维射线追踪，**但最终仍投影到二维**（因为 `costmap_2d` 的足迹是二维）。它计算开销大，更新延迟会造成转向时点云「拖影」残留，进而局部规划失效。
- 若机器人在平地/缓坡，「纯二维 `obstacle_layer` + 高度过滤（`max_obstacle_height`）」反而更稳、更快。
- 若地形含台阶、悬空杂物、高低差需要区分，才上 `voxel_layer` 或自研 `elevation` 层。

> **建议**：局部层默认用 `obstacle_layer` 保证实时性；**仅在「地形语义判据」场景切到 `voxel_layer` 或 `elevation` 层**，并记录切换前后的实时因子（Gazebo 的 `real time factor`）作为性能代价读数。这比一次性全上重层更能定位问题。

### 3.4 自研 `elevation` costmap 层开发规格（S1/S2 的正解）

这是一个约 200—300 行的 `costmap_2d::Layer` 插件，接口面很小：

```cpp
// elevation_layer.h  —— 骨架示意，非最终实现
class ElevationLayer : public costmap_2d::Layer {
public:
  void onInitialize() override;                      // 订阅 /elevation_grid，读私有参数
  void updateBounds(double&, double&, double&, double&,
                    double&, double&, double&) override;
  void updateCosts(costmap_2d::Costmap2D& master,
                   int, int, int, int) override;
private:
  ros::Subscriber sub_;
  grid_map::GridMap map_;      // 键：elevation, slope, step, rough
  // ★所有阈值从 <elevation>/ 前缀私有参数读，本件不给默认值
};
PLUGINLIB_EXPORT_CLASS(ElevationLayer, costmap_2d::Layer)
```

**参数命名（强制挂前缀，S2 硬要求）**：

| 参数 | 语义 | 值 |
|---|---|---|
| `elevation/slope_lethal` | 坡度致命阈值 | ★待定标（J1），本件不填** |
| `elevation/slope_inflate` | 坡度膨胀起点 | 待定标 |
| `elevation/step_lethal` | 台阶致命阈值 | 待定标 |
| `elevation/unknown_cost` | 未知区代价 | 待定 |
| `elevation/cost_scale` | 代价曲线系数 | 待定 |
| `elevation/deadband` | 噪声死区 | 待定 |

**开发顺序建议**（每步可独立验收，避免一次性调参）：
1. 只读 `/elevation_grid` 并 `ROS_INFO_THROTTLE` 打印统计（z 的 min/max/mean、非 NaN 比例）→ 证明数据通路通。
2. 全部格写 `FREE_SPACE`，与纯 2D 层对比 → 证明不破坏原有行为（**2D 回归不劣化**，正合 QB2 要求）。
3. 只开 `slope` 一项，调一条代价曲线，人工看 RViz 热力图是否与地形吻合。
4. 逐步加 `step`、`unknown`。
5. 把每步的 RViz 截图 + costmap 统计一起留档。

## 四、逐条问题对策

### 4.1 载体几何面（G1—G5）

| # | 困难 | 对策 | 需授权 |
|---|---|---|---|
| **G1** | 近场地面回波缺 | ①**新增空白对照景**：仅一张水平地面、无踏步无坡度、起始位姿退到 `R_min` 之外；②判据从「有没有点」改为「**距离—点数累积曲线**」（累积 10—20 帧）；③该景不含任何 step/slope 值 | 景归属需裁（见 §8 待裁 甲2） |
| **G2** | 缺口归因是几何 | ①**先定标 `h`**（`tf_echo`，Wave 0 第一件）；②用 `R_min = h / tan(θ_min)` 重算并**二选一写死基准**；③明确 3.99 m 是地面命中还是立面斜距 | 否（只读+计算） |
| **G3** | 机体无腿 | **拆两件载体**：A「导航态」刚体盒承载 L3 全部判据；B「步态态」12 关节承载步态判据。B 件可抄 Noetic 现成路（CHAMP / quadruped-robot / `lite3_description` 的 `gazebo_classic.xacro`） | 载体 B 属设计面 |
| **G4** | 返回域 ≪ 发射域 | **两路分开报**（已是在册规矩）：发射域报「看得境」，返回域报「命中境」，禁止互相推断；建议在采集脚本里同时落 `scan_zenith_emitted.json` 与 `scan_zenith_returned.json` | 否 |
| **G5** | 线数口径分裂 | **判掉，不并报**：`ring` 为发布侧常数标签（世界件空载亦然），在册 8 条为 T8 模型产物。口径改为 §5.1 四项（每帧束数／zenith 占用箱／方位非空箱／等效线密度）。**厂商口径为「等效 40 线」——50 与 32 均不符厂商，故「线数」本身应弃用** | 口径变更需裁 |

> **G2 的算术必须摆出来**（`tan 7.21° ≈ 0.1265`）：
>
> | `h`（雷达离地） | `R_min = h / tan(7.21°)` |
> |---|---|
> | 0.4347 m（J2 站立态读数） | **3.44 m** |
> | 0.505 m（由实测 3.99 反推） | 3.99 m |
> | 0.55 m | 4.35 m |
> | 0.59 m | 4.66 m |
>
> G2 用 `h = 0.55—0.59` 推「理论最近 4.2—4.7 m」，却拿实测 3.99 m 当「吻合」——**3.99 不在 4.35—4.66 区间内，它是更近的**，两者不能同时为真。且 `0.55—0.59` 与 `0.4347` 差 0.11—0.16 m，这不是标定误差量级，而是**另一套标定基准**（真机卷尺量雷达顶面 vs 仿真 TF 里 `livox_frame` 原点到地面）。用真机高度预测仿真读数、再用仿真实测「验证」该预测，是跨基准的循环论证。

## 五、口径统一（G5/W3 的可执行部分）

### 5.1 四个替代 `ring` 的观测量

| # | 观测量 | 算法 | 为什么具判别力 |
|---|---|---|---|
| 1 | **每帧束数** | `点云总点数 ÷ 帧数` | 厂商硬指标：200,000 pts/s ÷ 10 Hz ＝ **2 万点/帧**，最易被对拍抓住 |
| 2 | **zenith 占用箱数** | 众数 zenith 按 0.05° 分箱，报占用箱数 + 箱内点分布 | 反映射线集角分布；**必须带分箱粒度**才可比 |
| 3 | **方位非空箱数** | 360 分箱，报非空箱 | 抓扇区缺失、遮挡、图案裁剪 |
| 4 | **等效线密度** | 竖向 FOV 内每 0.5° 的占用箱数 | 把 50／32／40 三口径拉到同一把尺 |

**厂商基准（Livox MID-360 公开规格）**：竖向 FOV `-7°~+52°`（共 59°）、水平 360°、点率 200,000 pts/s、帧率 10 Hz、盲区 0.1 m、角精度 <0.15°(1σ)、距离精度 ≤2 cm@10 m / ≤3 cm@0.2 m、**点密度等效 40 线**。

> 由上式可见：在册 50 线与现跑 32 线**都不是厂商口径**。MID-360 没有离散 ring，只有连续 zenith 分布，「线数」是人为分箱的产物。**只要把名词换成「等效线密度」并强制携带分箱参数，这一整条争议自动消解。**

### 5.2 `mid360-real-centr.csv` 的 800,000 行须先定性

| 若 800,000 行是 | 含义 | 后果 |
|---|---|---|
| **一帧的射线总数** | 仿真每帧束数 ＝ 真实 40 倍（2 万 vs 80 万） | 近场检测能力被系统性放大 40 倍，**G1 全部「有没有点」的结论都要按此倍率重读** |
| **图案库**（40 帧轮转，每帧 2 万束） | 与真实一致 | G1 结论可原样使用 |

一条命令即可判：`python3 -c "import pandas as pd; d=pd.read_csv('mid360-real-centr.csv'); print(len(d), d.iloc[:,-1].nunique())"`，或直接看插件每帧实际 cast 的射线数（`gz topic -e /gazebo/default/...` 或插件里的 cast 计数）。

### 6.3 zenith 统计骨架（G5 正解，新建件，不动 `precheck.py`）

```python
#!/usr/bin/env python3
# zenith_hist.py —— 输出 4 个替代 ring 的观测量
import rospy, numpy as np, json
from sensor_msgs.msg import PointCloud2
import sensor_msgs.point_cloud2 as pc2

BIN_DEG   = rospy.get_param('~bin_deg', 0.05)
AZ_BINS   = rospy.get_param('~az_bins', 360)
FRAMES    = rospy.get_param('~frames', 100)
acc_zen, acc_az, acc_pts, acc_n = [], [], 0, 0

def cb(msg):
    global acc_pts, acc_n
    pts = np.array([[x,y,z] for x,y,z,_ in
                    pc2.read_points(msg, field_names=('x','y','z','intensity'),
                                    skip_nans=True)])
    if not len(pts): return
    r   = np.linalg.norm(pts, axis=1)
    zen = np.degrees(np.arcsin(np.clip(pts[:,2]/np.maximum(r,1e-9), -1, 1)))
    azi = (np.degrees(np.arctan2(pts[:,1], pts[:,0])) + 360) % 360
    acc_zen.append(np.round(zen / BIN_DEG).astype(int))
    acc_az.append((azi / (360.0/AZ_BINS)).astype(int))
    acc_pts += len(pts); acc_n += 1
    if acc_n >= FRAMES: report(); rospy.signal_shutdown('done')

def report():
    zen = np.concatenate(acc_zen)
    az  = np.concatenate(acc_az)
    out = {
      'frames':            int(acc_n),
      'total_points':      int(acc_pts),
      'beams_per_frame':   float(acc_pts) / max(acc_n, 1),   # ← 对比 20000
      'zenith_bin_deg':    float(BIN_DEG),
      'zenith_occ_bins':   int(len(np.unique(zen))),
      'zenith_span_deg':   [float(zen.min()*BIN_DEG), float(zen.max()*BIN_DEG)],
      'az_nonempty_bins':  int(len(np.unique(az))),           # ← 对比 360
      'eq_line_density':   float(len(np.unique(zen)) / (59.0/0.5)),
    }
    print(json.dumps(out, indent=2, ensure_ascii=False))

rospy.init_node('zenith_hist')
rospy.Subscriber('/livox/lidar', PointCloud2, cb, queue_size=1)
rospy.spin()
```

**注意**：此脚本只读点云，不参与任何判据，不写任何门值；输出是「读数」而非「结论」。
