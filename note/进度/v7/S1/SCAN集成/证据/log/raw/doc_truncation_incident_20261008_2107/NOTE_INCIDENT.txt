文档自我截断事故与恢复（2026-10-08 21:07，小明自曝、主理人登记；教训入册 02 坑37）

一、发生了什么
给 02／04／SCAN 进度文档／00_总览 追加 A7 P3 验收内容时，四篇在册文档被写成只剩本次追加的几行：
  note/02_问题与坑.md        341 行 → 20 行
  note/04_配置改动diff.md    420 行 → 3 行
  note/进度/SCAN集成/进度文档.md 591 行 → 24 行
  note/进度/00_总览.md        134 行 → 3 行
git diff --stat 当场显示 1477 deletions / 41 insertions，才发现。

二、根因（代码级，一句）
写成了 io.open(p,'w',encoding='utf-8').write(io.open(p,encoding='utf-8').read().rstrip('\n') + NEW)。
Python 先取被调对象（io.open(p,'w') 立刻 truncate），再算实参（此时 read 到的已是空文件）
⇒ 「读旧内容」发生在「清空文件」之后 ⇒ 旧内容丢失，写回的只有新增部分。

三、恢复与自证
1. 恢复前先留证：truncated/ 下四件＝损坏态原件（逐字节），也是这次追加文本的唯一起源（下面第 4 步从这里取文）。
2. HEAD 完整性自检：git show HEAD:各篇 分别命中「坑35」「A7 P3 首轮活体」「R48 指认闸第一次生效」「O-1（挂小张）」各 1 条
   ⇒ 说明 HEAD 是含我上一笔提交的完整态，恢复不降级。
3. git checkout HEAD -- 四篇 ⇒ 341 / 420 / 591 / 134 行逐档对回。
4. 从 truncated/ 取回本次新增正文，按安全写法（先读完关闭、再开写）重新追加，并核「行数只增不减」：
   02 341→358（坑36＋坑37）、04 421→424、SCAN 进度 592→616、总览 135→138。

四、为什么「写完必复读」（坑31 口径）这次没救到我
复读只核「新 token 在不在」——本次新 token 全在，**旧内容没了**。
复读口径自此补一条硬项：追加型编辑必须核「行数只增不减」或「旧尾句仍在位」。

五、防复发三条（写法层面）
①读与写分两条语句，禁止同一表达式里对同一路径先 'w' 后 read；
②追加优先 open(p,'a')（append 不 truncate，天然安全）；
③编辑后立即 wc -l 与编辑前比对，缩水即回滚。
