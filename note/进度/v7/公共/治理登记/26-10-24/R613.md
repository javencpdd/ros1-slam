## 一、坑98＝形检取数式选错了面

形检（每批手写进缓存区的一次性件、不入仓）按 `git diff --unified=0 -- <路径>` 取新增行、只检新增行里的禁形。批264 重提交那一轮是**先 add 再补跑** ⇒ 裸 `git diff` 比的是**工作树对索引**、此时两者一致 ⇒ 新增行＝0 ⇒ 三条锚点全报「辖域未命中」 ⇒ rc=5、红档 3 条。改一个词（`git diff HEAD`）后立刻 rc=0、辖域内 12 行。

**三处值得立坑的理由**：

1. ★它不是报错，是「看起来像结论」的空集***＝三条「★辖域未命中★ …（新增行 0 行、锚点 0 ⇒ 辖域空＝未证）」印得很完整，读者第一反应是「本批没写东西／锚点写错了」，往错的方向查。
2. ★与在册旧教训「提交后跑＝恒 0」是同一枚病的两半***＝旧教训说「跑得太晚」，本枚说「跑得太晚的另一形＝先 stage 了再跑」⇒ 合起来＝★形检的有效窗口比想象中窄得多★。
3. ★若脚本把空集当通过，同一枚缺陷会翻成恒绿＝空控***＝本件旧版就是把「段内 0 行」只降为提示行；本件没翻成恒绿，只因为作者当时顺手把「辖域空」写成了红。

**正形四条**＝①凡按 git diff 取新增行的判据，★必须显式写基准★＝`git diff HEAD` 或 `--cached`，★绝不写裸 `git diff`★；②★辖域 0 行一律拒判★，不许印绿、也不许当「没有新增」（坑29 在取数基准方向的亚种）；③★跑形检的时点钉成一句＝stage 之前、且相对 HEAD***；④★一次性脚本不入仓 ⇒ 这类教训必须落册***（脚本改好了，下一次不一定带得过来）。

## 二、坑99＝混合暂存态漏提交

批264 改动五处（四件已跟踪文件的修改 ＋ 一枚新建批次全文）。只对新文件 `git add` 就 `git commit -F`（不带 -a）⇒ 只提交了那一枚新文件，自印「1 file changed, 46 insertions(+)」。事后 `git show --numstat` 才发现只有 1 行 ⇒ 靠 `git reset --soft HEAD~` ＋ `git add -A <五处>` ＋ 重提交挽回（★该提交尚未推送故安全；已推送则属改写远端历史、本仓明令不做★）。

**为什么在册那条老规矩这次没报警**＝自印的「1 file／46 insertions」与实际提交**完全对得上**——它说的是真话，说的是★另一件事★（统计的是这次提交、不是这次改动）⇒ ★「自印对得上」不等于「改动都进去了」★。本枚是「自印短统计不可作对表依据」那条老规矩的★反例★，两条并读才完整。

**正形**＝①★commit 前逐行看 `git status -s` 的两列***＝第一列＝索引态、第二列＝工作树态；★出现「第二列 M、第一列空」即未暂存***；②同批既有新增又有修改时，★add 要一次给全路径***；③提交后一律 `git show --numstat` 对表，且★对表的对象是「本批打算改的面」清单、不是自印那一行***。
