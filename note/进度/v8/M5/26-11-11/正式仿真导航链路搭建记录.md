## 2. 踩到的四个真缺陷（都属"看起来能跑、其实跑不起来"）

1. **XML 注释里不能有 `--`**：我在 launch 注释里写的箭头 `-->` 直接让 roslaunch 报 `not well-formed (invalid token)`。改成 `=>`。
2. **catkin 的 relay wrapper 不能被 import**：`catkin_install_python(PROGRAMS goal_gate_policy.py ...)` 生成的是 relay 脚本——它把源码 `exec` 进一个私有 context dict，**模块本身不导出任何名字**。于是 `import goal_gate_policy; goal_gate_policy.parse_allowed` 抛 `AttributeError`。**这是我 04:32 那次"修复"引入的**。正解：入口用 `catkin_install_python`（wrapper 可执行），被 import 的模块用 `install(FILES ...)`（真实文件）。
3. **roslaunch 的 `type` 不接受子路径**：`type="planner/topic_node.py"` 报 `Cannot locate node of type ...`；`rosrun` 却接受。所以「甲方案（装入口）」对 runtime 有效，对 roslaunch 无效。正解：包根装重命名入口或写 `scripts/` shim。
4. **`catkin_make --pkg` 不执行 devel install 步骤**：改完 install 规则后文件不更新，必须手动 `cmake -DCMAKE_INSTALL_PREFIX=devel -P cmake_install.cmake`。而且 devel space **不清理旧产物**——旧的 wrapper 会一直留着，必须手工删。

## 4. 局部执行段：解除三道门槛，卡在第四道（18:56—00:50 续）

上一版把断点记成「`/cmd_vel` 没有 `/gazebo` 订阅者」。**那是误读**：`rosnode info /gazebo` 显示它确实订阅 `/cmd_vel`。真正的拒绝来自局部规划器自己——它在 `/v8/local/status` 里明说原因。

| 门槛 | 现象 | 处置 | 结果 |
|---|---|---|---|
| 定位有效 | `E_LOCAL_LOCALIZATION` | 位姿源补发 `/v8/local/localization_ok`(Bool)，心跳 **0.2 s**（判据是 `now - loc_received >= max_age_s`，`input_max_age_s` 默认 1.0 s，原先 1 Hz 正好卡边界） | **已解** |
| 支撑面 | `E_LOCAL_SUPPORT` | ★**根因找到**★：`local_native.Config.support_tol_m` 默认 **1e-6**（微米级），要求位姿 z 精确等于地图 `z_reference`；仿真载体是方盒、位姿取模型中心 z≈0.11，而 `z_reference=0`，差 0.11 m 直接判"不在支撑面上"。launch 里按"脚底接触高度带"的本意放宽到 0.25 | **已解** |
| 障碍新鲜 | `E_LOCAL_OBSTACLES_STALE` | ★**根因（双层）**★ 第一层＝残值假象：启动瞬间 obstacles 未连上，tick 把 `E_LOCAL_OBSTACLES_STALE` 写进 `last_error`，而 map 缺失导致主循环在「map 为空」处空转、永不覆盖它，`stop_reason` 无目标时返回 `last_error` ⇒ 新鲜输入也被旧残值顶着展示。第二层＝真陈旧：`sim_empty_obstacles` 用 `rospy.Timer(Duration)` 按**仿真时钟** 2 Hz 定时，而 freshness 判据用**墙钟**（`time.monotonic`，max_age 1.0 s）；实测本机 **RTF≈0.446**（仿真时间 10.009 s / 墙钟 4.461 s），sim 2 Hz 折算墙钟只有 0.9 Hz ⇒ 心跳周期 1.12 s 恒超 1.0 s。位姿 50 Hz/定位 0.2 s 因频率高 4—10 倍幸免。修法＝launch 提到 sim 10 Hz（RTF 0.45 时墙钟 4.5 Hz、年龄 ≤0.22 s）＋补上 map 发布（见 §4b） | **已解** |

**关于「无目标时读 status」的坑**：没有目标时 `stop=true`、`velocity=[0,0,0]` 本来就是正常态，`stop_reason` 会把早期一次失败锁存下来。必须先发目标再读，否则读到的是历史值——我因此绕了两轮。

第四道已排除的五项：

1. 消息格式：直接调 `native._obstacles([])` 返回 `[]`，不抛异常；
2. 话题连通：`rostopic info` 双向确认（发布者 `/sim_empty_obstacles`、订阅者 `/v8_local_planner`）；
3. 参数覆盖：`obstacles_topic` 走默认，与发布一致；
4. **回调确实执行**：加 `[local] obstacles ok: 0` 日志后每 5 秒稳定出现（拒绝分支计数为 0）；
5. **时钟同源**：`controller.tick(lambda: rospy.Time.now().to_sec(), time.monotonic, ...)` ⇒ `wall_now` 与 `obstacles_at` 都是 `time.monotonic`，不是跨钟比较；
6. `stop_reason()` 是 `fresh` 优先、锁存次之，所以报 stale 说明 `fresh` 本身返回了 stale。

**剩余方向**：`on_obstacles` 里的 `shared` 闭包对象与 `tick` 取快照用的 `shared` 是否为同一 dict（是否有重新赋值而非 `update`）。下一步在两条日志里同时打印 `obstacles_at` 与 `id(shared)` 对比即可定论。

**定论（23:30 后续）**：`self.shared = shared` 是同一引用，该假设证伪。真正的判据面证据来自两条新仪表：①status 新增 `input_ages`（三路输入实时年龄，与 freshness 同一判据面）——无 map 时读到 `obstacles=0.579 < max_age=1.0` 却仍报 stale ⇒ 残值假象实锤；②status 新增 `obstacles_cb`（回调计数）＋ worker 失败消息附输入快照。另「12—13 秒一条日志」是 **stdout 管道块缓冲假象**（rospy.loginfo 进 roslaunch 重定向管道被 8 KB 块缓冲），不是回调饿死；看真实回调频率要读 `/rosout`。

## 4c. 载体动了之后的两道关（坐标系与物理贯穿）

| 关 | 现象 | 根因 | 修法 |
|---|---|---|---|
| 垂直分量 | 局部规划器报 `E_LOCAL_VERTICAL_UNSUPPORTED` | 路径点 z=0（支撑面基准）而位姿 z=0.11（模型中心），轨迹生成 -0.11 垂直分量，`map_to_body_planar` 对 vz>1e-6 拒发 | `sim_pose_source.py` 加 `z_offset=-0.11`（模型中心→支撑点换算），map 坐标系 z 语义回到「支撑点高度」 |
| 微米贯穿 | 载体行驶到 0.6 m 处精确卡死，`E_LOCAL_NO_ROUTE`（worker 快照：start z=-1.93e-05、goal=(2.05,0.05,0)） | Gazebo 接触物理 ~20 µm 软贯穿 ⇒ 支撑点 z 小幅低于面顶；`local_native.py:613` 自面豁免用硬编码 `SUPPORT_TOL_S=1e-6`，z 低于面顶 1 µm 即判「嵌进地板」，全部邻居被碰撞判定拒绝。实测 z=-1e-5 必失败、z=+1e-4 正常（非对称实锤） | 夹具层：`sim_pose_source.py` 加 `z_snap_band`（默认 2 cm），[-band,0) 吸附回 0——支撑点语义上不能低于所站的支撑面。**★待真人裁：规划器层 `SUPPORT_TOL_S=1e-6` 对真机毫米级接触贯穿同样过紧（真机 z 噪声必撞同款），建议与 `support_tol_m` 统一或放宽，属判据变更、不属本补丁授权★** |

锁存行为的说明：`E_LOCAL_NO_ROUTE` 是锁存型 reason，一次失败置 `stop_latched` 后主循环停发；但 `accept_goal` 收到任意新目标（path_goal 每 ~2 s 随全局重规划重发）即清锁存——此前停死不是锁存缺陷，而是**每次重规划都因 z 为负再次失败**；z 吸附修复后自愈链生效。

## 8. 坡面到达预算按路径长度缩放，复验 outcome=reached（2026-11-12 傍晚）

### 8.1 改动

`lite3_bt` 新增 `include/lite3_bt/arrival_budget.hpp`（纯 stdlib 函数）＋`test/test_arrival_budget.cpp`（8 项，`check_console.sh` 编译执行）。`bt_console` 增订 `/global_path`（`nav_msgs/Path`，参数 `~path_topic`）算折线长度；`WaitArrival::onStart` 冻结一次预算：

```
budget = max(tree timeout, path_length / arrival_speed_floor_mps)   # 默认 floor 0.02 m/s
```

- 树端口 `timeout="60"` 保留为**下限**，短目标行为不变；缩放只对长路径生效。`arrival_speed_floor_mps:=0` 关闭缩放。
- **只在 onStart 冻结一次**：全局规划器按移动中的 start 每 2 s 重规划，剩余路径长度会一路变短；若每 tick 重算，预算会在半途缩到小于已耗时间而误判超时。
- 规划器拒发/取消时发布的空 `Path` 不带长度，不借给下一次到达。
- `package.xml`／`CMakeLists` 加 `nav_msgs`；`bt_console.launch` 增 `path_topic`／`arrival_speed_floor_mps` 两个 arg（`test_bt_config.py` 的 key 面同步，10 项全过）。
- 附带修掉一个**第二次踩到的构建坑**：`catkin_make --pkg` 不执行 `install(FILES)`，devel 空间里的 relay wrapper 侧没有 `goal_gate_policy.py`，goal_gate 启动即 `ModuleNotFoundError`（11-11 一次、11-12 一次）。`CMakeLists` 增 `lite3_bt_devel_policy` 自定义目标，每次构建把模块同步进 devel；实测删文件后重建自动恢复。

### 8.4 E_LOCAL_CLOCK 追根与 A/B（同日，L2 待裁）

§8.3 的遗留不是「无害瞬态」，而是坡面慢的主因。用同一个 bag 拆开看：
