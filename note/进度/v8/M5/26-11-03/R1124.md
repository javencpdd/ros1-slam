## 一、结论（先回答“能不能直接用”）

| 问题 | 结论 |
|---|---|
| 能下载吗 | 能。`ros1` 分支 143 MB；`setup.sh` 列 43 个 Fuel 模型（README 正文写 42），实测 43/43 下载成功，解压 56 MB |
| Gazebo 11 能加载吗 | 能。三个 world 均 headless 加载成功；无缺模型错误，只有 SDF version/材质/OBJ 非致命告警 |
| 楼梯需要驱动吗 | **不需要**。楼梯嵌在 `floor_01_walls` 的视觉/碰撞网格里，是静态碰撞；0.20 m 级高、±3 m 共 30 级（两个 3 m 行程各 15 级） |
| 电梯需要驱动吗 | **需要额外插件**。car/door/portal 三件都是 `static=1`、1 link、0 joint、0 plugin；现在只能当装饰，不能呼梯/开门/移动 |
| 能直接做多层导航吗 | 不能直接签。两层/三层 world 是把同一层复制到 z=3/6；楼梯也被复制，上层楼板在楼梯上行段足迹处有开口（几何检查），但本次没有跑机器人上楼梯 |
| 能直接签 formal 吗 | 不能。只是导入探针；无机器人、无传感器、无地图、无导航、无物理通行证据 |

**一句话**：这是一个能加载的 rich hospital 资产包；楼梯是静态几何、不需要驱动，电梯是静态道具、需要写插件；
作为单层 SLAM 富场景或“楼梯 scoped 测试”的候选是可行的，但不能当成开箱即用的电梯多层或 formal 世界。

## 三、楼梯、电梯与坡道（含口径更正）

**楼梯**：不能按“模型名里没有 stair”就说没有。`aws_robomaker_hospital_floor_01_walls` 的
视觉网格含 `aws_robomaker_hospital_floor_01_stairs` 材质子网格，碰撞网格 `ID12` 有 252 个顶点；
它是**静态碰撞**，没有 joint/plugin。碰撞 bbox（DAE 厘米、Y-up）：
`x 1705.83..2094.26`、`y -299.97..300.00`、`z -1244.25..1244.18`，即约
**3.88 m 宽 × 6.00 m 高 × 24.88 m 长**。竖向每 0.20 m 一级，共 30 个间隔；
下半段（y -3..0）宽 1.88 m、长 20 m，上半段（y 0..+3）宽 1.88 m、长 12.52 m，
y=0 处有 landing。踏步进深偏长（低多边形长踏步），不是普通 0.30 m 进深楼梯。

**上层可不可达**：`floor_01_floor` 碰撞网格在上行段足迹处不是实心楼板（10 cm 点采样覆盖率
0.360；下行段足迹 0.948），与“楼梯井开口”一致；但这是**几何检查**，不是机器人通行验证。
单层 `hospital.world` 有天花板在 3 m，楼梯上行段会顶到天花板；楼梯测试应使用
`hospital_two_floors.world`（上层楼板在 z=3）。

**电梯**：`aws_robomaker_hospital_elevator_01_car/door/portal` 三件均
`<static>1</static>`、1 link、0 joint、0 plugin；world 里分别是 6/10/14 个实例。
car 不能升降、door 不能开、没有呼梯接口。要功能电梯，必须另加 lift 插件和门关节。

**坡道**：`aws_robomaker_hospital_ramp_01` 也是静态；碰撞网格约 2.45 m × 2.43 m、
rise 0.176 m，放在电梯口，是门槛/坡道，不是 3 m 楼层连接器。

**多楼层方式**：两层/三层 world 不是独立建模的二/三层平面，而是把 floor 1 的
floor/walls/ceiling/家具/楼梯整块复制到 z=3/6（每层 120 个 model 块）。因此：
- 楼梯被复制了两/三份；第一份的上行段可通向上层楼板开口；
- 复制层自己的下行段/再上行段会形成额外/死端几何；
- 本次只验证了“能加载 + 源几何有开口”，没有跑机器人或 support_map 上楼梯。

## 六、复现

完整命令见 `evidence/R1124/commands.txt`。最短路径：

```bash
# 1) 取 ros1 分支（默认分支只有归档 README）
git clone -b ros1 https://github.com/aws-robotics/aws-robomaker-hospital-world.git aws_hospital_probe

# 2) 资产：官方 setup.sh（需 python3-pip + requests/lxml/docopt）
cd aws_hospital_probe && ./setup.sh
#    本机缺 pip/docopt，改用同一 43 模型清单直接走 Fuel API

# 3) 加载（独立 master，避免碰 11313/11345）
docker exec -d ros1-slam-sim-viz bash -lc '
  source /opt/ros/noetic/setup.bash
  export ROS_MASTER_URI=http://127.0.0.1:11413
  export GAZEBO_MASTER_URI=http://127.0.0.1:11455
  export GAZEBO_MODEL_PATH=/opt/ros1-slam/data/imports/aws_hospital_probe/models:/opt/ros1-slam/data/imports/aws_hospital_probe/fuel_models:/usr/share/gazebo-11/models
  export GAZEBO_RESOURCE_PATH=/usr/share/gazebo-11:/opt/ros1-slam/data/imports/aws_hospital_probe
  exec gzserver /opt/ros1-slam/data/imports/aws_hospital_probe/worlds/hospital_two_floors.world \
    -s libgazebo_ros_api_plugin.so --verbose'

# 4) 读数
rosservice call /gazebo/get_world_properties
gz stats -d 3
```

## 八、补充：向下射线没有在 DAE 坐标假设下找到楼梯面

在 two-floor world 里加了一个 static 单束向下 ray（`z=4.5`，`/stair_probe/scan`），
用 `/gazebo/set_model_state` 移动采样，想直接确认“楼梯碰撞面 + 上层开口”在运行时是否对齐。
读数（完整 CSV 见 `stair_ray_line.csv` / `stair_ray_grid.csv`，摘要见 `stair_ray_scan.txt`）：

- 控制点：`(0,0)` 打到 `z=3.0000`（上层板/天花），`(30,0)` 打到 `z=-0.1000`（地面），
  说明射线与移动链路有效。
- 在 DAE bbox 推出的假设带 `x=17.2..20.7, y=0/±5/±10`：全部只打到 `z=-0.1000`（地面），
  **没有** 0—3 m 的楼梯面。
- `y=0` 线扫：`x=-9..11` 打到 `3.0000`（上层实心楼板），`x=13..21` 打到 `-0.1000`（地面）；
  `x=±20, y=-12..12` 也全是地面。
- 侧翼网格只在 `z=3.03..4.12` 打到板/构件，均不是 0—3 m 楼梯面。

**这不推翻“源网格里有楼梯”**：`floor_01_walls` 的碰撞 DAE 确实有 `ID12`（252 顶点、
0.20 m 级高）。它说明的是：**不能把 DAE bbox 直接当 world 坐标**；楼梯在 world 中的摆放、
碰撞是否按预期加载、复制层的上层开口是否与上行段对齐，都还没有被这次快速射线检查确认。
因此本批不签“楼梯可通行”；要继续必须用点云/support_map 或机器人跑一次，而不是靠 bbox 推断。

本补充不改变主结论：楼梯是静态几何、无需驱动；电梯是静态道具、无插件；formal 未签。
