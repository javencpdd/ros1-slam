## 1. 坏夹具（已作废，保留为反例）

`force_crawl.py stair --xml Lite3.xml`（无世界台阶）时，`run_stair` 用 `load_model` 在内存里加一块
`x=1..5、高 0.06` 的台阶；但 `crawl_gait` 的落足逻辑按 `step_h` 给目标，实际四足从未过 x=1.0：

- start 0.70/0.72/0.75/0.80 各跑一次：`world_feet_end` 四足 x 全在 0.90—0.96；
  `force_experiment=[]`（力控桥接**从未激活**）；所谓“4/10 步”是平地步。
- 同夹具下 force 与 pd 逐位相同（32 相位完全一致），因为力控桥接只包住后腿摆动，
  而这次失败在 advance/shift，根本不在其激活窗口。

⇒ 该批 8 个 JSON 只作**夹具反例**，不作台阶结论。

## 3. 判读

- **③ 力控后腿（按现实现）不是解法**：它确实把 plain 的首个失败（`advancer0_HL_b` 滑移）
  消掉了——force 的 r0 HL/HR advance 全过——但代价是后腿抬升被压到 4—5.6 cm，
  三条后腿抬升全部 `lifted=False`；随后 r1 HL 的 advance 滑移 18.1 cm、drive_ok 也失败。
  这是“解决了 A 却引入 B”，需要先修力控的高度/法向力分配，不能算打通。
- **① 两级踏面（低台阶）不是解法**：世界 0.04 m 台阶与 0.06 m 一样 **5/10**、
  同一点 `advancer0_HL_b` 滑移；前足已真实落在阶面（z=0.061），后足悬空。
  逐级高度不是约束，后腿推进/支撑策略才是。
- **② 斜向接近**仍未测（当前准静态架构无偏航控制）；**④ 暂缓**仍可行。
- 与 R833/R834 的结论一致：瓶颈在「前两足上阶后、后腿推进」的桥接期，不是台阶高度或控制类型。

## 4. 边界

1. `force_crawl.py` 自载 `experimental: true`、`hardware_validated: false`；世界件与第三方 MJCF 未改。
2. 有效读数各 n=1；世界 0.04 是单级低台阶，不是字面“两级踏面”楼梯——但已足以说明
   逐级降高不改变失败点；字面两级楼梯未跑。
3. 未改 `crawl_gait`/`force_crawl` 默认值、未改判据、未把力控收为正式方案。
4. 不构成四足跨层或真机证据。
