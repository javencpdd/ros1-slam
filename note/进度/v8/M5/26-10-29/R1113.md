# R1113 · R1064 同 lab 挂起根因：reap 关闭被 reader 锁住的 stdout

- 时间：2026-11-02 04:10—04:52 CST（qoder）；性质＝间歇挂起根因修复
- 代码：`396709ce`（reap 修复＋SIGUSR1 栈）＋`8ab300bc`（每例唯一 local 名、每 lab 独立 Gazebo master）
- 证据：`evidence/R1113/`（hang_stack、hang、5 次 clean run、summary、command、tests、code_ref、hashes）
- 容器：ros1-slam-sim

## 一、复现与根因

5 次同 lab soak 中复现：某次跑到 `sensed_no_route` 后 130 s 仍存活，
`/a5_gazebo_*/status` 无新消息，local 节点与 4 个 adapter 并存。
对 `a5_gazebo_runtime` 发 `SIGUSR1`（faulthandler）得到主线程栈：

```
main -> run -> run_case -> stop_owned -> OwnedChild.reap
     -> self.proc.stdout.close()
```

daemon reader 线程仍阻塞在 `read1()`；`BufferedReader.close()` 等其 buffer 锁，
于是 `reap` 永久阻塞——这就是 R1064 的“第三例后挂起”。

## 二、修复

- `OwnedChild.reap` **不再关闭 `proc.stdout`**；保留 terminate→wait→kill→wait，
  reader 继续以 daemon 线程读取到 EOF 后自行退出；
- local 节点名改为每例唯一 `a5_owned_local_<pid>_<case>`，避免残留同名节点；
- `runtime_lab` 为每次 lab 分配独立 `GAZEBO_MASTER_URI`（ROS port+1），
  避免跨跑 Gazebo/11345 冲突；
- 新增 `SIGUSR1` faulthandler，下一次挂起可直接取栈；保留 20 s status 看门狗。
