# R667／批320：支撑图规划节点运行面首证（容器内发布＋独立检查）

更新时间：2026-10-26

## 1. 本片做了什么

把 R666 的适配层真正跑起来：固定镜像内起 roscore，节点读取 support_map JSON，发布 nav_msgs/Path 与状态参数，另起独立检查器订阅同一话题，逐点核对是否落在支撑面足迹内、frame 是否为 map、诊断字段是否齐全。

结果：检查器输出 `{"ok": true, "points": 5, "frame": "map", "status": {"ok": true, "segments": [{"surface": "ground", "cells": 5}], "transitions": [], "expansions": 4, "length": 2.0}, "bad": []}`。

## 2. 运行面暴露并修掉的真问题

| 现象 | 根因 | 处置 |
| --- | --- | --- |
| 预检宿主侧 rc9 | 本机无 /opt/ros/noetic、ws 无 devel | 改在固定镜像内跑同一无参预检，rc=0 后开窗 |
| rosparam 报无法连接 master | 覆盖 PYTHONPATH 时把 ROS 路径冲掉 | 改为在既有 PYTHONPATH 后追加 |
| 节点启动即崩 | ROS_LOG_DIR 指向只读路径 | 指定容器内可写日志目录 |
| import support_planner 失败 | 该模块依赖 contracts/validate.py | 挂载 contracts 并加入 PYTHONPATH |
| 检查器等不到消息 | 私有话题名解析为 /节点名/support_route | 显式用全局话题名，并由节点打印实际话题名 |
| 单次发布丢消息 | 发布后节点立刻退出，latch 随发布者消失 | 节点保持存活（keep_alive_s 可调），发布端 latch |
