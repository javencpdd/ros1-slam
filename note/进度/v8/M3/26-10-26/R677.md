# R677／批327：消费链接入的接口判定与三个选项（需真人勾）

更新时间：2026-10-26

## 1. 已核实的事实

- `mbf_msgs/GetPathAction` 存在，`mbf_costmap_nav` 包在位；但该 action 是 **MBF 自己提供的**服务端。我们另起一个同名 action server 只是并行接口，不会被 move_base 消费。
- `move_base` 的 `make_plan` 走**进程内** nav_core 插件，外部服务挂不上（前批文档核对已确认）。
- 镜像内**没有** `nav_core` 开发头（`/opt/ros/noetic/include/nav_core/nav_core.h` 不在位），因此现在无法直接编译 `nav_core::BaseGlobalPlanner` 插件；`mbf_costmap_core` 虽有包，也要对应头与插件接口。

## 2. 三个选项（请勾一个）

| 选项 | 做法 | 代价/风险 |
| --- | --- | --- |
| 甲（推荐） | 在**私有**镜像副本或私有工作区补 `nav_core`/`mbf_costmap_core` 开发头，写最小 `BaseGlobalPlanner` 插件，catkin 构建后由 move_base 进程内调用；出「真实进程内调用到本规划器且路径非空」读数 | 需新增私有环境包；不动主镜像与共享卷 |
| 乙 | 不写插件，把「外部 GetPath 服务」定为正式接口，move_base 进程内接入选为后续集成任务（V8-07/13） | 零新增依赖，但 A4 的「被消费」证据停留在动作级，不是 move_base 级 |
| 丙 | 用 MBF 原生 planner 插件接口（`mbf_costmap_core`）写插件，让 MBF 自身调用本规划器 | 与甲类似，依赖 MBF 版本接口，配置面更大 |

## 3. 现状

动作级消费证据已齐（R674 墙钟、R676 仿真时钟），缺的只是「move_base/MBF 进程内」这一档。未做任何环境安装；未改第三方、未 push。
