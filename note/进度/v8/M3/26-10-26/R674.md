# R674／批325：GetPath 动作服务打通（成功有路径、拒绝有码）

更新时间：2026-10-26

## 1. 三个真因

| 现象 | 真因 | 修法 |
| --- | --- | --- |
| 动作客户端构造即报错 | `mbf_msgs/GetPath` 目标字段是 `target_pose`，不是 `goal` | 客户端与服务端都改用真实字段 |
| 动作「挂起」 | 生命周期用仿真时钟算超时，停钟/未起钟时恒为 0 | 改单调墙钟；盖戳前最多等 10 s 墙钟拿非零仿真时钟 |
| 返回 SUCCEEDED 但空路径 | `SimpleActionServer` 的 execute 回调收到的是 **goal 消息**，不是 handle；`get_goal()` 不存在，异常后动作被当成功 | 回调签名改为 `getpath(goal)`，改用 `server.set_succeeded/set_aborted` |

## 2. 读数（墙钟隔离对照，只起 roscore）

| 项 | 值 |
| --- | --- |
| 服务连上 | true |
| 成功路径点数 | 18 |
| 成功结果码 | 0（SUCCESS） |
| 图外目标 | 结果码 53（INVALID_GOAL），空路径，消息带 E_PLAN_GOAL_INVALID |
| 客户端判据 | 成功必须非空、拒绝必须为空，两者同时成立才 ok=true |

证据：[sim_R674](sim_R674)（世界、图、脚本、检查器、check.out）。

## 3. 遗留与边界

- 拒绝消息里理由码重复了一次（`E_PLAN_GOAL_INVALID: E_PLAN_GOAL_INVALID: ...`），是拼接所致，属文案瑕疵，未改。
- 这是**墙钟模式**下的动作证据；仿真时钟模式（`use_sim_time` + gzserver）下的动作读数下一片补。
- 仍不是 move_base 进程内消费：这是 MBF `GetPath` action，实际接入还须 MBF 侧配置或 nav_core 插件。
