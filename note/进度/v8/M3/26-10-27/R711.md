# R711／批360：Gazebo 深度相机输出恒为 3.0 m——判死，改走 MuJoCo 深度渲染

更新时间：2026-10-27

## 1. 读数（把这条链判死）

| 项 | 值 |
| --- | --- |
| 世界模型 | `support_ground`／`support_step1`／`support_landing`／`camera_rig` 都在 |
| `/cam/depth` | 32FC1、320×240、307200 字节 |
| 深度直方图 | **MINMAX 3.000 / 3.000**，全部 76800 像素同一个值 `3.0` |

即：该插件在本镜像里**只输出常量深度**（相机高度），台阶（0.18/0.36）完全没有体现。换俯仰方向也拿不到有效几何（另一方向直接零命中）。

结论：**`libgazebo_ros_depth_camera.so` 这条路不通**，不是参数问题，是输出本身不可用。

## 2. 改走哪条

已在环境里跑通的 **MuJoCo**（同一台容器、`mujoco==2.3.7`）自带离屏渲染与深度缓冲：
- `mujoco.Renderer(model, height, width).update_scene(data)` + `enable_depth_rendering()` 可直接拿到深度图；
- 场景用我们自己的三级台阶（0.0／0.18／0.36），相机放在上方俯视；
- 由深度图反投影得到**观测高度列**，再聚类成三条高度带——这是**观测**，不是场景声明。

## 3. 为什么这也符合红线

- 观测来源明确标注为 `observation:mujoco-depth`，与「场景声明高度」严格区分；
- 不修改任何第三方文件，只在私有目录写采集脚本；
- 生成的 `support_map` 仍要过 `validate.py`，再跑规划核验。

## 4. 下一步

1. 用 MuJoCo 渲染器在三级台阶场景取一帧深度，反投影出高度列；
2. 交叉验证三带 ≈ 0.00/0.18/0.36；
3. 通过后生成 `support_map`（`source.uri=observation:mujoco-depth`）并跑规划，闭 `#139/#145`。
