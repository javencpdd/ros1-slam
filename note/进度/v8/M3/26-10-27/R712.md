# R712／批361：观测高程链打通——MuJoCo 深度 → 三条高度带 → support_map → 规划 38 点

更新时间：2026-10-27

## 1. 读数（这是观测，不是场景声明）

用 MuJoCo 离屏渲染（`MUJOCO_GL=osmesa`）在三级台阶场景取一帧深度，按内参反投影后按高度聚类：

```
BANDS [(-0.00, 42005 px), (0.18, 6675 px), (0.36, 8455 px)]
```

三条带与几何真值 **0.00 / 0.18 / 0.36 完全一致**（这就是交叉验证）。

再由观测点生成 `support_map`（`source.uri = observation:mujoco-depth`，`data_uri` 同源），
`validate.py` 通过，`support_planner` 出路径：

```
{"surfaces": ["obs_0","obs_1","obs_2"], "z": [-0.0, 0.18, 0.36],
 "points": 38, "segments": 3, "transitions": 2}
```

## 2. 为什么这条算数

| 要求 | 落实 |
| --- | --- |
| 必须是观测而非场景声明 | 高度来自深度图反投影；`source.uri` 明确标 `observation:mujoco-depth` |
| 不得用场景声明顶替 | 未从 XML 读取任何高度；只从渲染深度计算 |
| 仍须过契约 | `validate.py` 校验通过（三面、足迹、step 边、可达） |
| 仍须能规划 | 38 点、3 段、2 次转层，与 R689 的设计层结果一致 |

## 3. 边界（不夸大）

- 观测来自 **MuJoCo 离屏渲染**，不是 Gazebo 深度相机（后者整幅常量 3.0，已在 R711 判死），也不是真实传感器；
- 这证明「深度观测 → 高程带 → 支撑图 → 规划」链路可用，**不等于**高程算法（V8-08 生产者的聚类/证据规则）或 SLAM 通过；
- 台阶级高由场景几何给定（0.18/0.36），观测只是复现它们，不构成「任意地形泛化」的证据。

## 4. 结论

`#139 高程源→support_map` 与 `#145 私有域最小高程生产者` 的**最小链路已闭合**，证据见本目录 `mj_map.py`／`mj_obs.py`／`obs_map.json`／`result.txt`。
