# FAR 后端评估（2026-11-25）：当前场景下不适配，保留为实验后端

## 一句话
FAR 建不出可见性图（始终 1 个顶点）的根因**不在 FAR 算法、也不在 V8→FAR 适配层**，而是
**HDL 的 map 系相对 odom 抬高约 1.05 m、俯仰偏约 12°**，使地形在 map 系整体悬空约 1.5 m，
"地面"与"障碍"的语义判据全部失效。Support 后端不依赖 z，因此不受影响（仍 4/4 PASS）。

## 可复现证据

测量条件：机器人先搬到 (5.2, 2.45)，再以同一点初始化 HDL（`asan_hdl_repro.sh` `INIT_X/Y`），
`P3_VERDICT=PASS`，`/hdl_odom` **单发布者**，随后启动 FAR 图。

| 探针 | 读数 |
| --- | --- |
| `scripts/verify/terrain_tf_ab_probe.py` raw(rslidar) | n=20000，z 中位 **0.00**，**88.6%** 落在 ±0.1 ⇒ 原始点云里地面点充足 |
| 同上：TF 直接变换到 map | z 分位 1%=1.27 / 中位 **1.50** / 99%=2.70，z<0.1 占 **0.0%** |
| 同上：`/terrain_cloud`（far_node 产出） | z 分位 1%=1.27 / 中位 **1.50** ⇒ **与直接变换逐位一致**，适配层没有额外抬高 |
| TF 分量 | `odom→base_link z=0.11`、`base_link→rslidar z=0.34` ⇒ 合应 0.45 |
| TF 复合 | `map→rslidar z=1.50`、pitch ≈ 3°（而 URDF/TF 的 base→rslidar 是 15°） |
| 推出 | `map→odom z ≈ 1.05`，且 map 相对 odom 俯仰偏约 12° |

结论：**适配层忠实地把点云搬到了 map 系**；悬空来自 map 系本身。

## 为什么这会摧毁 FAR
`utility.cpp:200-221` 用 `p.intensity < terrain_free_Z(0.2)` 判"可通行"，而我们的
`intensity = 点高 − 地面高`。地图整体悬空 1.5 m 后：
- 逐格最低点把**墙面**当成地面 ⇒ `h≈0` ⇒ 91% 判 free（无自由边界可言）；
- 若强行给 `terrain_ground_z=0.0` ⇒ 所有点 `h≈1.5` ⇒ 100% 判 obs（全堵死）。
两种都给不出可用地形，实测 `/v8/3d/global/path` 均 0 帧。

## 与 Support 的差异（为什么 Support 不受影响）
Support 后端吃 2D 支撑栅格（`/v8_support_map`）+ `(x,y)` 位姿，**不用 z**；
FAR 是 3D 地形规划器，**完全依赖 z 的正确性**。同一套 HDL 位姿对前者够用、对后者不够。

## 处理决定
1. FAR 保持**实验后端**，不参与 Support 主线验收，也不阻塞 Support 的 4/4 PASS。
2. 适配层新增的 `~terrain_ground_z`、`terrain_flatten` **保留**（默认不变），供将来地图 z 对齐后使用；
   FAR 图里**不做覆盖**（避免在错位地图下把全图判成障碍）。
3. 要启用 FAR，前置条件是先修 HDL 的 map 对齐：
   - 手段候选：改用与 world 同源的 PCD（现用 `mapped_m1.pcd`，其 z 中位 0，本身正确）；
   - 或核对 HDL 的初始位姿/`robot_odom_frame_id` 与 NDT 收敛结果，把 `map→odom` 的 z 与 pitch 拉回 0；
   - 判据：`map→rslidar z ≈ 0.45 ± 0.05` 且俯仰与 base→rslidar 一致（15°）。

## 2026-11-26 复核（P0 坐标契约）：结论改写

**原判定「FAR 算法不适配」不成立**，改为 **「输入契约阻断、待验收」**。原读数被两个数据缺陷污染：

1. **`/rslidar_points` 72.9% 是精确零点**（14579/20000，插件未命中射线写成 (0,0,0)）。
   原评估里「z 中位 0.00、88.6% 落在 ±0.1 ⇒ 点云已被压平」正是这批假点造成的假象：
   剔除后同一帧的非零点地面拟合是 **倾角 15.00°、传感器到地面垂距 0.450 m**，与 URDF 外参
   （base→rslidar `z=0.34`、`pitch=15°`，加 odom→base_link `z=0.110`）**逐项吻合** ⇒ 点云本来就在 rslidar 系，
   没有压平、也没有重复套外参。修法：`sim_adapter.repack_cloud` 按插件 `<range><min>0.1</min>` 剔除。
2. **地图与世界观不同源**。原评估用 `mapped_m1.pcd`（实采，x∈[−2,14.8]、带累积漂移）去配
   `m1_world.world`；换成同源 `m1_world_synth_v1.pcd`（x∈[−2,7]，与世界几何一致）后，
   NDT 不再用"倾斜"去凑：**map→odom pitch 由 −11.9° 降到 −0.6°**，**map→rslidar 0.49 m / 14.4°**
   （判据 0.45±0.05、俯仰随 15° 安装角）。

原「map→odom 抬高 1.05 m」不是独立的 z 误差，而是 **pitch −11.9° 作用在 5.17 m 力臂上的结果**
（0.206×5.17≈1.06）。这也解释了旧探针为何给出"地形整体悬空 1.5 m"。

**旧探针本身也不成立**（已重写 `terrain_tf_ab_probe.py`）：它取两份不同点云、（用 `Time(0)`）拿最新 TF
去搬旧帧、只比分位数——三条叠加正好把"零值假点"读成"坐标系被压平"。

**FAR 侧现状（同一套 M1 地图/HDL/感知/控制，仅换后端）**
- 可见性图能建：启动即 `Number of global vertices: 95`（原为 1）
- 地形/路径出得来：`/terrain_cloud` 2.5 Hz、`/v8/3d/global/path` 2.5 Hz、`global status ok=true points=2`，
  路径首点＝当前位姿 (5.09,2.40)、末点＝目标 (3.90,2.45)
- **仍未通过**：机器人不动，`/v8/local/status` 报 `E_LOCAL_COLLISION` ⇒ 执行链被地形/障碍层挡住，
  与残留 ~0.2–0.5 m 竖向偏移同源。属"逐格最低点/地形高度"这一类独立问题，不能因 TF 修好就假定适配层正确。
