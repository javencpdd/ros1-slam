## 1. 问题的可观测形状

三句话，每句都有读数支撑（出处见第十一节 11.2.1）：

1. 适配器自己判故障时走 `/v8/local/cancel`（第二写者），BT 只当它是「执行层回执」，**不置取消意图**；
2. 于是树停在 mission 的 `WaitArrival` 里，机器人已停、位姿不再前进，唯一出口是到达预算到点
   （`max(60, L/0.02)`，2 m 腿 100.2 s，10 m 腿 500 s 量级）；
3. 这期间重发的目标**只入队不被取**（队列上限 16），表现为「操作员看着没事，车就是不动」。

## 2. 8 秒窗探针（已实现）

### 2.1 为什么必须换判据

旧判据「最终是否出现新时间戳路径」等得够久必然变 True —— mission 超时进 Recovery 后队列照样会被
pop。于是它**同时容纳「立刻接」和「100 秒后才接」两种事实**，没有分辨力。
本探针把观察窗钉死在 **8 秒**，而预算地板是 **60 秒**，小一个量级。

### 2.2 时间轴、判据、两个模式

| 时点 | 动作 |
|---|---|
| `t0` | 发取消（`--mode direct` 发 `/v8/local/cancel`；`--mode bt` 发 `/v8/bt/cancel`） |
| `t0+3.0` | 发目标 2（与 `_regoal_via_bt.py` 的等待同量级；8 秒窗里留 5 秒给 BT 反应） |
| `t0+8.0` | 收窗、判读，三条判据各自报值 |

| 判据 | 含义 | 为什么它能分辨 |
|---|---|---|
| J1 `/v8/global/goal` 上出现目标 2 坐标 | `RequestPath` 真跑了 ⇒ BT 取队了 | 取队后毫秒级发，与后端快慢无关 |
| J2 `/global_path` 出现 `t0` 后新时间戳帧且点数 ≥ 2 | 全局后端真出了新路径 | 依赖后端，故只作并列判据 |
| J3 `/v8/bt/status` 的 `goal_seq` 变大 | `WaitForGoal::takeGoal` 真 pop 了 | BT 自己的计数，不依赖任何后端 |

模式的意义：`direct` **期望 FAIL**（这就是要留的修复前证据）；`bt` **必须 PASS**（反控：证明探针
对本该接上的情形不失灵，不是恒红空控）。探针自己打 `SW_DISCRETING`（见运行日志），
两模式结果符合预期才算「探针有分辨力」。

### 2.3 与 `run4` 判据的差别（一句话）

`run4` 判「取消后**最终**有没有新路径」，本探针判「**8 秒内**有没有」——前者是存在性，后者是时效性。
同一个修复前系统，前者 PASS、后者 FAIL，这正是两条判据的分工。

### 2.4 首轮跑出来一个新发现：缺口只在「取消落在 ARRIVAL」时成立

第一版探针（`probe_run1`、`probe_run2`）跑了 4 轮 `direct`，结果是 **3 轮 FAIL、1 轮 PASS**。
那轮 PASS 不是探针坏，日志把因果写得很清楚：

```
round_direct2（probe_run2）
[bt] goal 1 dequeued (0 waiting)                 sim 3.048
[bt] global path requested for goal 1            sim 3.049
[bt] global path refused: E_FAR_HALTED           sim 3.771   ← 阶段①：取消打断了路径请求
[bt] goal 2 dequeued (0 waiting)                 sim 4.799   ← 50 ms 内就被取走
[bt] global path ready (2 points)                sim 4.978
```

⇒ 根因不是「BT 永远傻等」，而是**取消落在哪个节点，结局完全不同**：

| 取消落点 | BT 侧发生什么 | 8 秒窗 | 真正的问题 |
|---|---|---|---|
| **PATH_PENDING**（路径还没 ready，停在 `WaitForPath`） | FAR 改发 `E_FAR_HALTED`，它**不在** `transient_plan_reason` 白名单里 ⇒ `WaitForPath` 当场 `FAILURE` | PASS（很快） | 不是卡死，而是**队列里的目标被自动接着执行**（`goal 2` 50 ms 内被取）——正是「故障停之后自己又跑起来」 |
| **ARRIVAL**（路径已 ready，停在 `WaitArrival`／`FollowPath`） | 位姿不再前进、没有任何判据 ⇒ 只能等满预算 | FAIL（卡死） | 本卡标题说的那个 |

**这条发现改变了设计**：丙案不能只解决 ARRIVAL 相位的等待，还必须同时处理 PATH_PENDING 相位的
「自动接着跑」（§4）。验收也必须按相位分开跑，否则同一模式两次读数会一个 FAIL 一个 PASS，
看上去像探针不稳。

**探针据此改了两处**（`probe_run3` 起生效）：
1. 新增 `SW_CANCEL_PHASE`（取 `/global_path/status` 的 `ok` 与 `points` 判 ARRIVAL／PATH_PENDING），
   把自变量记下来；
2. 首帧路径之后再 settle `1.5 s` 才发取消，让 `direct` 轮**稳定落在 ARRIVAL**（否则落点是随机的）。

`SW_EXPECT` 也随落点算：只有 `direct + ARRIVAL` 才期望 FAIL；`direct + PATH_PENDING` 期望 PASS
（那是快路）。`SW_DISCRIMINATING=False` 表示**本卡的因果假设被否**，不许当读数错误糊过去。


## 3. 丙案：把执行层回执升格为取消意图

### 3.1 四问

**Q1 · seq 从哪来**

| 来源 | seq 取值 | 现读出处 |
|---|---|---|
| BT 自己（`CancelStop`） | `g_state.cancel_seq`（不另增） | `bt_console.cpp:694-702` |
| BT 自己（`StopExecutor`） | `++g_state.cancel_seq` | `:766,771` |
| 适配器自诊断 | `CANCEL_SEQ_BASE = 900000000` 起单调 | `far_node.py:34,279-282` |
| 操作员走 BT 入口 | 任意，BT 取 `max(自增, 帧内 seq)` | `:1127` |
| 操作员违规直发 | 任意（无约束） | — |

ack 帧是 `<seq>:<outcome>`，由执行层回显它收到的 seq（`local_planner/ros_node.py:266`）。
⇒ **seq 只是「哪一条取消」的标识，本身不含来源信息**。这是 Q2 的前提。

**Q2 · 来源怎么识别**（四法对照，选第 2 法）

| 法 | 做法 | 代价 | 结论 |
|---|---|---|---|
| 1 号段白名单 | 只认 ≥900000000 的 seq 为外部 | 0 行 | 否：BT 不该知道适配器的号段；操作员直发任意号就不被识别；号段撞车即失效 |
| **2 自持已发集合** | BT 记录自己 publish 过的 seq（有界 16），ack 的 seq 不在集合内 ⇒ 外部 | ~10 行 | **采用**：不依赖任何对方约定，假设最少 |
| 3 帧扩字段 | ack 带 `<source>` | 改执行层 + 改帧语义 | 否：执行层本来也不知道发起者是谁 |
| 4 新话题 | 执行层另发 `/v8/local/fault` | 新接口 + 双侧改 | 否（本卡不采用，列入 §5 对照） |

**Q3 · 与 mission 状态怎么关联**（三重，缺一即误触发）

1. `has_current == true` —— 只在「有当前目标」时认这条 ack；空闲期收到的 ack 一律只记账不动作；
2. `seq ∉ self_issued` —— 排除 BT 自己发起的回执（含 BT 转发的操作员取消）；
3. `seq ∉ cancel_results` —— 去重，防同一条 ack 被反复处理（该 map 已存在，上限 128，`:1152-1154`）。

时间窗不作为判据：ack 帧里没有时间戳，用「到达时刻」判迟到只会把慢执行层误杀。改用集合去重 +
`self_issued` 有界记忆（16 条）来挡回放与迟到。

**Q4 · 误触发面**（逐条给挡住它的机制 / 或明确「挡不住」）

| # | 场景 | 会被误触发吗 | 靠什么挡 / 代价 |
|---|---|---|---|
| 1 | BT 自身取消后的 ack | 否 | `seq ∈ self_issued` |
| 2 | 操作员走 BT 入口取消 | 否 | BT 转发用 `max` 后的 seq，同样在 `self_issued` |
| 3 | 操作员违规直发 `/v8/local/cancel` | **会**（且这是想要的兜底） | 不是误触发，是把违规路径救回来；甲案规范不变（两处并存不矛盾） |
| 4 | 迟到 ack（上一目标取消的回执） | 否 | `seq ∈ self_issued`（16 条记忆）+ `cancel_results` 去重 |
| 5 | 重复 ack / 同 seq 重发 | 否 | `cancel_results` 去重 |
| 6 | 后端切换后旧执行层回放 | 部分 | 同 4／5；若执行层重启后从旧号重来，会被当新事件（**已知残留**） |
| 7 | 适配器重启后 seq 回退（回到 900000000） | 会被当成新事件 | 这是**想要**的：重启后的第一次故障必须能救。代价是不能用严格单调判据 |
| 8 | 执行层回 ack 但没真停 | 会提前进 Recovery 并发零速 | 方向是 fail-safe（停比跑安全），可接受；要求 `last_event` 记 `ack_cancelled_external` 便于判因 |
| 9 | 后端根本不回 ack（move_base/TEB 链） | 不会触发 | 丙案对该后端**无效**，适用范围＝执行层是 `v8 local_planner` 的两条链（support 与 far 共用 `run_local_planner.py`） |

### 3.2 最小改动形状（伪码；2026-11-22 夜已按此落地，实做偏差见 §8.2）

```
// 新增：自己有界记忆（16）
std::deque<std::uint64_t> self_issued;      // 只在 :702 与 :771 两处 publish 前 push

void cancelAckCallback(msg) {
  parse(seq, outcome);
  lock;
  bool mine = contains(self_issued, seq);
  bool known = g_state.cancel_results.count(seq) > 0;
  g_state.cancel_results[seq] = outcome;        // 保持既有记账
  if (outcome != "cancelled") return;           // 只有真停才升格
  if (mine || known) return;                    // Q3-②③
  if (!g_state.has_current) return;             // Q3-①
  g_state.cancel_requested = true;
  g_state.cancel_reason = "ack_cancelled_external";
  g_state.cancel_scope  = "current";
  g_state.last_event    = "cancel_adopted_from_ack";
  // 见 §4：同一处清队列，防旧目标自动恢复运动
  g_state.pending.clear();
}
```

改动量实测估计：**10—20 行**（原诊断件写 6—10 行偏低，主因是 `self_issued` 记忆与清理队列两段是
必需的，不能省）。

### 3.3 与甲案的关系

甲案（操作员取消一律走 `/v8/bt/cancel`）是**规范**，丙案是**兜底**：甲案管「人怎么做」，
丙案管「执行层已经自停了之后，树怎么别傻等」。两者并存不冲突；丙案落地也不改变甲案要求，
但会让「违规直发」从「卡死 100 秒」变成「立刻停」——这一点要在运维文里写明，免得有人拿它当正规入口。

## 4. 故障必须安全停止：旧目标不得自动恢复运动

### 4.1 现状为什么违背这条要求

`Recovery(skip)` 结束时只把 `has_current` 置 false（`:923-929`），**队列不动**。下一轮 tick 到
`WaitForGoal` 就 pop 下一条 —— 于是「故障停止」事实上变成了「停一下然后自己接着跑」。
`run1`（`b2_probes`）日志里 `goal 6 dequeued (11 waiting)` 那一串就是这件事的现场：11 条排队目标在
mission 收尾后连珠炮式执行。

本轮探针又抓到一个更直接的现场（`probe_run2/round_direct2/launch.log`）：取消落在 PATH_PENDING 相位，
`WaitForPath` 被 `E_FAR_HALTED` 当场拒 ⇒ mission 立刻收尾 ⇒ **50 ms 后 `goal 2 dequeued` 并被派发**
（`follow path -> dispatch goal 2, 1, 0.11`）。也就是说：**故障停止后，队列里的目标会自动恢复运动，
不需要任何人再下命令**。这正是要求 4 要禁掉的行为。

### 4.2 处置（丙案内一并做，仍是同一处回调）

升格取消时 `g_state.pending.clear()`，并记 `pending_dropped` 计数进 `last_event` 或状态帧，
便于事后判「这次停丢了几条」。现有 `cancelCallback` 只在 `scope == "all"` 时清（`:1132`），
而第二写者帧里的 scope 不可靠 ⇒ **故障停止语义下不看 scope，一律清**。

### 4.3 trade-off（必须写明，不要含糊）

清队列 ⇒ **取消即彻底停，想继续必须显式重发**。这与「取消后重发目标能被接」（第十一节第 9 条
那一实验）并不矛盾：那条测的是「重发的新目标被接」，清的是「取消前排队的老目标」。
如果业务上需要「取消后自动接着跑剩下的航点」，那是另一个决策（要区分「故障停」与「任务暂停」），
本卡不做，也不许用一个开关含糊两件事。

## 6. 验收标准（修复后按此判，七条全过才算修）

1. **ARRIVAL 相位转绿**：`--mode direct` 在取消落点＝ARRIVAL 时，8 秒窗内 J1/J2/J3 全绿；
   两轮独立运行读数一致（判据见 §7.1 的表，修复前是 FAIL）。
2. **反控不回归**：`--mode bt` 仍 PASS；`run4` 那四条判据（转发／ack／占位帧／新路径两点）仍全绿。
3. **PATH_PENDING 相位不倒退**：该相位修复前本就 PASS（靠 `E_FAR_HALTED` 被
   `WaitForPath` 当场拒），修复后必须仍 PASS，且**不许**把 `E_FAR_HALTED` 加进 BT 的瞬态白名单来
   「让它更顺」—— 那会把故障伪装成「规划还在跑」。
4. **旧目标不自动执行**：`--queue-old` 场景（取消前先塞 3 条旧目标）下，解除后 8 s 内
   `goal_seq` 不增、无新路径、`pending_dropped>=1`。**两个相位都要测**：§7.2 的 `PATH_PENDING`
   那轮已经抓到「50 ms 内自动接着跑」的现行行为。
5. **support 后端零回归**：同一探针在 `global_backend:=support` 下行为不变（该链同样回 ack，属面内）。
6. **误触发面**：构造「BT 自身取消 + 迟到 ack + 同 seq 重发」三种输入，要求既不重复升格、也不误清无关队列。
7. **红线不动**：`git diff` 不含 `60_safety`、`local_native`、树 XML；`arrival_speed_floor_mps` 仍为 0.02；
   任何以缩短预算为手段的方案不得入选。

### 8.2 与 §3.2 伪码的三处偏差（逐条给理由）

### 8.3 判据为什么不是「一重」

真人的第 6 条要求：不能仅凭「seq 不在自持集合」就认定是适配器故障。落地后的四重事实（`cancel_origin.hpp`）：

| 重 | 事实 | 挡的是什么 |
|---|---|---|
| 一 | `outcome == "cancelled"` | 被拒／未确认的 ack 没有停任何东西 |
| 二 | `seq ∉ self_issued` | BT 自己（含代操作员转发）的取消 |
| 三 | `seq ∉ cancel_results` | 迟到 ack、同 seq 重发（该 seq 已了结过） |
| 四 | `has_current` | 空闲期到达的无关 ack 不得把取消意图挂到下一条 mission 上 |

四重全真才升格。十六组真值表里有且只有一组落到 `EXTERNAL_STOP`，逐条翻转任意一重都退回 `RECORD_ONLY`——
这条「只有一个格子是红」的断言就是防止判据漂成恒真／恒假的主测。

★第四重的上界比设计时想的宽（2026-11-22 夜活体实测，见 §8.8 表 8-7 `idle4`）★：`has_current` 在
**mission 成功收尾时不清零**（全仓只有 `CancelStop` 与 `Recovery` 两个置假点），所以「手里还有活腿」
这个前提在空闲期恒为真。真值表那一格仍然对，但它验的是「传进去的 `has_current==false`」这个**输入**，
不是「空闲期 `has_current` 真的为 false」这个**事实**——这两件事必须分开报，不许拿单测绿去覆盖活体红。

### 8.5 ★新增发现：PATH_PENDING 相位仍会自启动旧目标（未闭合，须单独裁）★

**现象**（`probe_fix3/round_direct2/launch.log`，时间戳为仿真时）：

```
4.847  [bt] goal 2 dequeued (2 waiting)              ← 队首旧目标被取走（探针发到达信号所致）
4.847  [bt] global path requested for goal 2
5.006  [local] cancel accepted seq=900000001         ← 第二写者取消（执行层同步回 ack）
5.032  [bt] global path refused: E_FAR_CANCEL_RECEIVED
5.040  [bt] goal 3 dequeued (1 waiting)              ← 旧目标 2 秒内被自动取走
5.241  [bt] follow path -> dispatch goal 2, -1       ← 并真的派发出去
```

**机制**（比「回执没升格」更细一层）：

1. 适配器收到同一条 `/v8/local/cancel` 后，在**它自己的回调里**立刻发一帧 `E_FAR_CANCEL_RECEIVED` 到 `/global_path/status`；
2. 该 reason 不在 BT 的瞬态白名单（`bt_console.cpp` 的 `transient_plan_reason`）里 ⇒ `WaitForPath` 当拍判 FAILURE；
3. 这次 FAILURE 与随后的 `Recovery(skip)` 发生在**同一个 `tickRoot()` 里**，`has_current` 当场被清；
4. 回执虽然只晚 25 ms，但 rospy／roscpp 的回调只在**该轮 `spinOnce()`** 里执行——而 `spinOnce()` 在一轮
   `tickRoot()` 之后。⇒ 回执被处理时 `has_current` 已经是假，第四重事实不成立，升格不触发；
5. 下一拍（50 ms）`WaitForGoal` 取队首旧目标并派发。适配器 `on_goal` 收到新目标就**解除 halted**
   （`far_node.py`「新 goal：解除 halted」）⇒ 旧目标真的跑起来。

**为什么 ACK 改法结构上挡不住**：判据要的是「这条取消是不是冲着我这条腿来的」，而这条腿在回执被处理之前
就已经被另一条通道（路径状态）判死了。这是两条通道的**同一 tick 内顺序问题**，不是判据松紧问题。
本进程是单线程 spinner（`main()` 里只有一处 `ros::spinOnce()`，无 AsyncSpinner），所以不存在内存竞态，
只有「消息先到哪一条」的顺序差——但顺序差足以让队列安全判据失效。

**最小补充方案（未实施，等裁）**：把第四重事实由「腿还活着」放宽为「腿刚刚死掉」——

```
// SharedState
double last_leg_end_at = -1.0;          // has_current 置假处（Recovery / CancelStop）打时间戳
// classify 的第四重
bool leg_recent = g_state.has_current ||
                  (now - g_state.last_leg_end_at) <= 2.0;
// 升格时若 has_current 为假：只清队 + 记账，不置 cancel_requested（没有腿可停，也没必要多播一条取消）
```

改动量 6—8 行，仍在同一处回调 + 两个置假点。**误触发面**：无关 ack 若恰好落在任一腿结束后的 2 s 内会被
当成故障停（多清一次队 + 多一条 `external_cancel` 记录）；该 ack 必须是 `cancelled` 且 seq 既非自持也未
了结，所以「无关」本身已经很窄。**不能走的那条路**：把 `E_FAR_CANCEL_RECEIVED` 加进瞬态白名单——
§6.3 已经明令禁止（会把故障伪装成「规划还在跑」），且它只解决这一种 reason，换个 reason 又复现。

**结论**：本相位判为**未修**。不得宣称「FAR 自停后 BT 快速恢复」已整体解决；已修的是 ARRIVAL 相位
（卡死）与「故障停后清队」这一半。

★2026-11-22 深夜状态更新★：本节的「未修」是当批结论，**已被 §8.10／§8.11 闭合**——这一相位改由
甲通道（线上帧）与乙通道（后端回显）在 `WaitForPath` 判失败**之前**直接停腿，不再依赖回执与腿位。
上面那条「2 秒窗」最小补充方案**没有采用**（理由见 §8.10.1），本节留作对照。

### 8.10 第二施工段：把「谁停的」判到任务关联上（闭合 8.5 与 8.8）

真人 2026-11-22 追加授权的四条必须与三条禁令，原文要点：必须解决 PATH_PENDING 相位故障停后旧目标
自启动、idle 期 `has_current` 未清导致的过触发、无关／迟到／重复 ACK 误触发，并保持 ARRIVAL 已修
功能不退化；**不许**放宽 2 秒窗、不许缩短超时、不许靠 seq 号段猜来源；必须有明确的任务关联与取消
状态判据；无 ACK 场景单列验证；**所有验收通过后再结卡**。

#### 8.10.1 8.5 的「腿刚死掉 2 秒窗」为什么没采用

三条理由，任一条都足以否掉它：

1. 它是**时间量**判据，正撞真人明令的第一条禁令；
2. 它只覆盖「回执晚到」这一种时序，覆盖不了 §8.5 的**真因**——同一 `tickRoot()` 内路径状态先判死、
   回执下一轮 `spinOnce()` 才被处理；
3. 它答不了「这条停是不是冲着这条腿」。时间上挨得近，不等于任务相关；一条无关回执落在窗口内
   照样会误停（8.8 的 `stray` 就是这种样本，只是它当时恰好落在窗口外）。

替代它的是**四条都不含时间量**的事实：号是不是本节点发的（精确集合）、这一拍有没有腿
（`has_current`）、是不是已经在取消态（`cancel_requested`）、这个号有没有第二个通道作证。

| 通道 | 话题 | 携带什么 | 何时到 | 单独能不能停腿 |

#### 8.10.5 一次外来停只升格一次（`already_latched`）

上一版留在盘上的实证（`probe_v2/round_direct2/launch.log`）：**同一个号被两条通道各升格一次**，
于是日志里两条「cancel this node did not issue」、`cancel_origin` 被后到的通道覆盖：

```
5.517  [bt] cancel this node did not issue (external_wire, seq=900000001, current goal 2): 2 dropped
5.400  [bt] cancel this node did not issue (external_ack,  seq=900000001, current goal 2): 0 dropped
```

修法：判类前先看 `cancel_requested`——**已经在取消态就只记不升**。改后同一场景每轮只有 1 条
（`probe_v3` 五轮 `external_cancel` 全为 1），且 `cancel_origin` 保留**先到那个通道**的名字。

#### 8.10.6 逐腿清账＝任务关联的落点

`takeGoal` 取到新腿时清掉 `external_cancel_seq` 与 `foreign_seqs`。理由不是洁癖：不清的话，上一段
任务里被记账过的号会给**下一段**的回执作证——一条迟到的旧号回执足以停掉一条刚起步的新腿，这正是
真人第 3 条要求里的「重复 ACK 误触发」。**不动 `self_issued`**：那是身份不是证据，且它按自增号
分配，跨腿天然不重叠。

#### 8.10.7 无活腿时也要清队（`dropStaleQueueLocked`）

场景：外来帧落在「上一条腿刚收掉、队列里还压着旧目标」的那一拍。这时没有腿可停，但队列属于一个
刚被外部杀掉的 mission——留着就意味着下一拍 `takeGoal` 把它派发出去，运动在执行层刚被叫停之后
自己重新开始。这正是真人第 1 条要求要防的那件事，只是相位从 PATH_PENDING 换成了「腿已收、队未空」。

三条约束：只对**帧通道**生效（回执通道一律不动队列，孤证回执必须零副作用）；单独计数
`stale_queue_dropped`（与「腿死了带走队列」的 `pending_dropped` 分开，事后能分辨是哪种）；日志不
借用「after fault stop」那句话（那一刻并没有故障停），实际输出：

```
[bt] cancel this node did not issue (external_wire, seq=900000008, no live leg):
     2 queued goal(s) dropped, no new motion without an operator goal
```

#### 8.11.1 无 ACK 场景单列

`noack` 与 `marker3`／`marker4` 是同一条通道的两种用法：**只有 `/global_path/status` 上的

回执本就是正常链路。★所以「无 ACK」指的是注入的那个号没有回执，不是收件箱为空★。

#### 8.11.2 探针自身的第三、四处缺陷（留档，别当产品缺陷）

1. **`noack` 的断言写成了「本轮没有任何回执」**：首轮实测 `MARKER_LATCHED=True` 而 `NO_ACK=False`
   判 FAIL——因为 BT 升格后用自己的号重发、执行层照常回执。改判「注入的那个号没有回执」后转绿
   （`probe_ackface3/`）。这与 §8.7-2「判定采样过早」同族：判据落在会变的旁观量上。
2. **`race` 的「队列里有 ≥2 条」用了 2 Hz 采样深度当前提**（`t1.06` 读到 `QUEUE_DEPTH=1` 而实际
   清了 2 条，于是把 FAIL 判在了前提上）。改判「清掉了 ≥2 条」（`pending_dropped`，由被清动作本身
   产生，不靠采样）后转绿。

#### 8.11.4 不得据此宣称

- 不得宣称「所有取消链路已闭合」：本段闭合的是**取消来源的判定**与**故障停后的队列安全**。
- 不得宣称「后端不回 ack 也已完全覆盖」：`noack` 证明的是「适配器回显存在时不依赖 ack」；

- 不得把 `bt5`／`bt1` 的绿读成「BT 的取消路径也被重写了」：它只证明新判据不误伤自己发的号。

### 8.12 第三次判据修正：为什么「新目标出路径」不能用「末点＝目标」判（2026-11-23）

#### 8.12.1 起因与结论先行

真人核查远端 `81acc4d6` 时指出：主矩阵四轮的 `SW_FRESH_PATHS` **全为 0** 却都判 PASS。那一版
`fresh_ok` 只验证「新目标已下发 + `goal_seq` 增长」，两件都是 50 ms 级逐腿事件，探针在 0.1—0.6 秒
就断言成功——**那时后端还没出路径**。结论：原来的 PASS 只证明 BT 恢复了接单，不证明 FAR 恢复导航。

本节的结论先摆出来，再给证据：

1. **规划链路没有坏**。逐跳实测显示新目标确实到上游、上游确实回了航点、`/global_path` 确实换相、
   `/v8/local/goal` 确实收到对应目标（表 8-13）。
2. **「末点＝操作员目标」不是规划事件，是到达事件**。上游在航点距机器小于 `local_planner_range`
   时会把航点沿航向外推 5 米；`/way_point` 变成目标本身只在它判出收敛那一拍。拿它当「恢复导航」
   的判据，判据就落在受车速与上游到达判据支配的代理量上（与坑 88／89 同族）。
3. **对照组也观察到较长收敛延迟**。不取消、直接换目标的对照组四轮为 12.9／13.4／15.0／18.0 秒
   （表 8-14）；但样本量小且两边都不是受控重复，**现有样本不足以确定故障恢复对收敛时间的独立影响**，
   因此本节不对「延迟是否由故障停造成」下结论。
4. 现判据改看确定性的**重规划里程碑**（六项，8.12.4），收敛时长降为读数如实报。

#### 8.12.3 为什么「末点＝目标」不能当判据

上游两处代码决定了这件事：

1. `ProjectNavWaypoint`（`far_planner.cpp:339-378`）：当航点与机器人距离小于 `local_planner_range`
   （本栈 5.0 m）时，**沿航向把航点外推 `free_dist - diff`**，使下发的航点恒在 5 米外。实测印证：
   机器人 `x=0.59` 时航点 `x=5.59`，差值恰为 5.00。
2. `PlanGlobalPath`（`graph_planner.cpp:163-178`）：只有判出「已收敛/到达」那一拍才
   `global_path.push_back(goal_ptr)`、`GoalReset()`、`is_goal_init_ = false`，此后 `/way_point`
   才等于目标本身。

⇒ `/global_path` 的末点等于目标，只发生在**机器人已经开到目标附近、上游宣布到达**的那一刻。
把这个时刻当「后端恢复规划」的判据，等于要求「先开到目标才能证明规划恢复了」。

**对照组实测**（`probe_ctl2/` 一轮 + `probe_ctl3/` 三轮，同两条目标、同样间隔，**不发取消**）：

**表 8-14 · 不取消、直接换目标的收敛时长（`_fresh_path_control.py`）**

| 轮 | 暖机路径 | 换目标后末点序列（相对时刻，秒） | 收敛 |
|---|---|---|---|
| `ctl2` | 0.8 s | 0.2 (2.0,0.0) → 8.3 (3.25,1.37) → 10.2 (3.49,3.17) → 12.0 (3.38,3.41) → 12.9 **(2.0,1.0)** | **12.9 s** |
| `ctl3-1` | 0.6 s | 同形（先游走、后落目标） | **15.0 s** |

对照组里 **0.2 秒那一帧也是旧目标 (2.0,0.0)**——「新目标后第一帧仍是旧航点」是上游回调排队的常态，
不是故障残留。

**两组的分母必须分清（本表口径）**：

| 组 | 尝试次数（分母） | 观测到收敛（有秒数） | 中位 | 范围 | 25 秒窗内未观测到收敛 |
|---|---|---|---|---|---|
| 带取消（`probe_path3`—`probe_v7` 多批合计） | **16** | **12** | 10.9 s | 6.9—24.9 s | **4／16** |
| 不取消对照（`probe_ctl2` + `probe_ctl3`） | **4** | **4** | 14.2 s | 12.9—18.0 s | 0／4 |

即：带取消侧的「12」是**观测到收敛的子集**，超窗计数「4」的分母是**全部 16 次尝试**，两者不可混用；
16 ＝ 12 ＋ 4。中位数只用 12 个有秒数的读数算，超窗率只能用 16 作分母（4／16）。

**结论怎么写才如实**：对照组四轮也都要 12.9—18.0 秒才把末点落到目标上，即「换目标后要十几秒」这个
现象在**没发取消**的对照组里同样出现；但两边都不是受控重复（对照组 4 次、带取消侧每批 1—2 次），
路程与上游收敛时机也不等同，**现有样本不足以确定故障恢复对收敛时间的独立影响**。因此本节既不下
「两者相同」「恢复侧不慢于基线」，也不下「延迟由故障停造成」或「与故障停无关」——观测到对照组也有
延迟，只否掉「延迟只在故障停后出现」，不等于否掉故障停对延迟有贡献。
support 后端三轮的收敛读数是 0.1 秒，属另一条规划器（没有上游图收敛这一步），不并入上表。

★这组数也解释了为什么"收敛"绝不能当判据★：同为带取消的轮次，一边 6.9 秒就落到目标、另一边 25 秒
还没落——差别只在机器人开到哪里、上游何时宣布收敛，与「规划是否恢复」无关。

#### 8.12.5 本轮暴露的四处探针缺陷（第五至第八处）

5. **链上旁证的下标抓晚了**：`/goal_point` 在派发那一拍就发出，等到「派发窗」结束（0.5—0.6 s）再抓
   下标正好漏掉它，读到 `GOAL_POINTS=[]`、一度错判成「适配器没转发新目标」。现抓在 `send_goal` 之前。
6. **重发逻辑把「派发成功但路径慢」当成「接单失败」**：旧版无条件重发，实测第二轮那条只在队列里
   排队（`goal queued depth=1` 之后再无 `dequeued`），既修不了路径，还往下一轮验收里塞一条没人执行
   的目标。现只在「没派发」时重发。
7. **对照组首版没等位姿**（`probe_ctl1`）：栈刚起来就发目标，位姿恒 `(0,0)`、机器人一步没动，上游退回
   静态环境的「前方 5 米虚拟点」(5.0,0.11)，两条目标都当没收到。该批读数作废；现先等
   `/v8/local/pose` 有值再等 3 秒（与主探针 `GOAL_DELAY_S=3.0` 对齐）。
8. **第③项被套到了没有该话题的后端上**（`probe_support4`）：`/goal_point` 是 far 适配器专有的中间
   话题，`support` 链整条没有它，于是六项里五项全绿、只有第③项恒假，两轮 support 全被判 FAIL。
   现按「暖机后链上有没有 `/way_point`／`/goal_point`」判这一项是否适用（`APPLICABLE`），不适用则
   跳过并打印出来。★「话题不存在」与「有话题但没转发」是两件事★——这类判据必须写清适用面。

另记一条**非探针缺陷但会误读的现象**：`probe_v4/direct1` 那轮机器人在 25 秒窗内位姿完全不动
（0.59→0.59），`/global_path` 末点恒为 (5.59,0.14)（＝位姿 + 5.00 的外推点），收敛读到 `None`。
按 §8.12.3 的口径它属「到达事件没发生」，不是「规划没恢复」——同一轮的 ③④⑤⑥ 四项全绿。

- 不得宣称「故障停后新目标会**立即**恢复导航」：带取消侧 16 次尝试里 12 次观测到收敛，
