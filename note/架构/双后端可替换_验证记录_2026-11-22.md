### 6.3 本节最贵的一条：`vehicle_height` 是「odom 离地高」，不是「雷达安装高」

far 分支起得来但 `WAYPOINTS` 恒 0、`/FAR_obs_debug` 恒 0、`/FAR_terrain_height_debug` 恒 0。定因过程与读数：

1. 纯合成台架（`evidence/b2_far_harness/`）能建图：`V-Graph Initialized`、36 航点 ⇒ 上游件与参数面没问题，问题在数据或时序。
2. 录一帧真实点云复放（`evidence/b2_far_recplay/real_cloud.npz`，19965 点、`obs_frac=0.145`）：位姿 z 用录值 0 → 失败；位姿 z 抬到 0.436 → 成功（`far_P1` vs `far_P4`）。用合成墙做同构造对照，`z=0` 失败／`z=0.436` 成功（`far_A/B/C/D`，交替 4 相，排除「第几相」的顺序效应）。
3. 把整片点云整体下移 0.436 也成功（`far_G`）⇒ 关键量是 **机器人与地面点的相对高差**，不是绝对 z。
4. 临时在 overlay 打点（已还原并核 42 件 sha256）拿到断裂点：`DIAG1 obs=77 → DIAG2 after_grid obs=77 → DIAG3 surround_obs=0`。写入成功、读取为空，抹掉它的是 `UpdateTerrainHeightGrid` 末尾的 `ObsNeighborCloudWithTerrain`。
5. 上游 `TraversableAnalysis`（`map_handler.cpp:459` 附近）启动地形连通搜索的条件是 `|terrain_h − robot.z + vehicle_height| ≤ height_voxel_dim(0.3)`。本栈 `/v8/local/pose` 的 z 与地面同高，故该差恒等于 `vehicle_height`；填 0.436 时 0.436 > 0.3 ⇒ 地形图不初始化 ⇒ 可见障碍格被全部滤掉 ⇒ 可见图不建。
6. 定为 0.0 后同一帧真实数据：`surround_obs` 0→131、航点 0→49（`far_K` vs `far_L`）。

`0.436` 是雷达安装高（`MID360_MOUNT_Z` 一族），与「odom 原点离地高」是两件事，不能互相回填。上游默认 0.75 同理是大型平台车的 odom 离地高。

### 6.6 补证据：把当时"只 print 不落盘"的读数重跑出来（`evidence/b2_probes/`）

见 6.1／6.2 的读数是当时终端上抄下来的，原始 stdout 一份没留——探针写在 `.git/` 下（不入库），

**一条接线事实（本轮最贵的一条）**：目标链是
`/v8/bt/goal` ＝[`bt_console` RequestPath]＝> `/v8/global/goal` ＝[全局后端]＝> `/global_path`。
**BT 才是目标所有者**。`far_accept.py` 的取消直接发 `/v8/local/cancel`（R6② 授权的第二写者），
BT 对此不知情、树仍停在 mission 分支 ⇒ 此时再往 `/v8/bt/goal` 发目标没人接，`REGOAL_NEW_STAMPS`
恒 0。**6.2 表里那个 `REGOAL_NEW_STAMPS=1` 极可能是取消窗口边界上的残留帧，不是"恢复产出"**——
这说明当时的读数虽然"数值好看"，但判据没有分辨力。
走真实入口重测（`_regoal_via_bt.py`，`run3`／`run4` 两次一致）：

```
REGOALBT_CANCEL_FORWARDED=True          # BT 把 /v8/bt/cancel 转成 /v8/local/cancel
REGOALBT_CANCEL_ACK_CANCELLED=True      # 同 seq 的 cancelled ack
REGOALBT_ON_GOAL_PLACEHOLDER=1          # 该帧只由适配器的 on_goal 发 ⇒ 目标真到了适配器
REGOALBT_NEW_PATH_POINTS=2              # 之后的新时间戳路径是两点式
状态序列：E_FAR_HALTED → E_FAR_WARMUP → {"ok": true, "points": 2}
```

`run3` 第一版判据写的是"末点须落在新目标附近（≤0.5 m）"，实测 `tail=(5.012, 0.112)` 判 FAIL。
**那条判据本身不成立**：FAR 发的是它自己图上的航点，不是操作员目标点（6.3 的 `vehicle_height`
定因也证明航点由可见图决定）。已撤并换成就绪帧＋新路径两点，这不是"放宽到能过"——目标若被忽略，
既不会有 `E_FAR_WARMUP` 占位帧，也不会有新时间戳的路径。

**顺带登记一条真实行为缺口（未修，属新决策族）**：第二写者取消后 BT 仍停在 mission，直到
`arrival timeout`（实测约 100 s，`[bt] arrival timeout after 100.2 s`）才进 Recovery；这期间
操作员再发目标，BT 不响应。要修得动 BT 或改树，按 R4—R7 不动 BT，故只登记。

**另起句指针（T-20261122-03 追加，原句不回改）**：上一段有两处措辞不准，已在**第十一节**更正——
①「不响应」的实情是**目标入队但不被取出**（`goalCallback` 只 `pending.push`，pop 发生在
`WaitForGoal`，mission 在跑时轮不到它），不是目标被拒；②「约 100 s」不是常数，是
`max(60, L / 0.02)`（`bt_console.cpp:95` 的 `arrival_speed_floor` 缺省 0.02），该腿 L≈2.0 m
才有 100 s，10 m 腿会到 500 s 量级。诊断链、五个方案的代价与越界判定、探针规格见第十一节。

## 十一、未修缺口诊断：第二写者取消后重发「不响应」（`T-20261122-03`，零改代码）

本节只做两件事：把 6.6 末段那条缺口的**机理钉到行号**，并把**修法与判据**摆到可裁的程度。
一行代码没改（`git diff --stat ae672cb9 -- ws/src/90_platform/lite3_bt` 为空），故下文全部结论的
性质是「诊断 + 规格」，不是「已修」。

### 11.1 先把措辞改准：不是「目标被拒」，是「入队不被取」

原句写「操作员再发目标，BT 不响应」，容易被读成目标被丢掉。现读 `goalCallback`（`bt_console.cpp:956-974`）：
它只做 `g_state.pending.push(item)`，队列上限 16（`:1197-1199`），**满了才拒**并打
`[bt] goal queue full`。所以重发的目标是**被收下的**，只是没人取——`pop` 发生在
`WaitForGoal::takeGoal`（`:187` 的函数体，取队在 `:197`），而树在 mission 分支里跑，
`WaitForGoal` 根本没被 tick。

⇒ 可观测差别很具体：日志里会先出现 `[bt] goal queued (depth=1, max=16)`，然后 100 s 里
**没有** `[bt] goal N dequeued`。**判据必须落在「取队」或「新路径」上，落「是否收到目标」上必假绿。**

★一条此前没人提过的附带结论★：队列是**有界**的，上限 16（`bt_console.cpp:1197-1199`）。

也就是说这个缺口不只是「慢」：持续重发会先把队列填满，再把后续目标**真拒掉**。

### 11.3 三个成因（为什么这套设计会这样，而不是「忘了写」）

1. **取消意图只有一个合法写者**：BT 认的是自己发起的 seq（`cancel_results` 按 seq 存，`:1152`），
   别人发来的 seq 只当「执行层的回执」看。这是**有意的**——`far_node.py:341-344` 的注释把话说透了：
   「`/v8/local/cancel` 已经有 BT 这个写者；回声会造成同一 seq 两次发布，而且会把「谁停的」这件事搅浑」。
   换句话说，第 5 环的「不置位」是设计取舍，不是漏写。
2. **mission 是 Sequence，没有抢占语义**：取消只能从 gate 或节点内部早退；队列只保证「不丢目标」，
   不保证「多久被接」。
3. **停滞没有判据**：树里 `progress_timeout="0"`（`navigate_with_planner.xml:20-21`，注释在 `:17-19` 明写
   「enabling it on the real robot is a physical criterion and needs a signed work order」）
   ⇒「停住不动」这件事本身不触发任何东西，只能落到预算超时。
