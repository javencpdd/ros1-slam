# 22 · 组件契约与组合架构

> v8 设计合同｜2026-10-24｜由 [21 中心计划书](21_ros1-slam中心计划书-v8.md) 派生。
> 以下为拟实现的接口与行为要求；仓内尚未实现统一注册表、求解器或编排器。示例只说明数据形制。

## 1. 组件职责与包装边界

| role | 输入/输出职责 | 首批来源或实现 |
| --- | --- | --- |
| odometry | 传感器 → 连续局部位姿与质量信息 | faster-lio 适配；仿真真值为独立测试组件 |
| global_localization | 地图＋观测 → 全局位姿、重定位状态 | hdl 系候选，须通过稳定性验证 |
| mapping | 位姿＋观测 → 地图更新 | 现有建图链适配 |
| map_server | 地图加载、坐标/版本与查询服务 | 平面地图、点云地图、多层地图分别声明 |
| representation | 观测/地图 → 算法需要的空间模型 | costmap_2d、多层支撑图、局部占据场 |
| global_planner | 起终点＋地图 → 带约束的路线 | GP/Navfn 适配；新增多层支撑图搜索 |
| local_planner | 全局路线＋局部观测 → 局部轨迹 | SCAN 适配或自持备选 |
| controller | 路线/轨迹＋状态 → 速度建议 | TEB/DWA 可作为规划与控制一体后端；SCAN 跟踪器适配 |
| trajectory_validator | 候选轨迹＋地图/机器人模型 → 可执行/拒绝原因 | 自持检查器，独立于候选规划器 |
| safety_arbiter | 多来源建议＋健康状态 → 最终运动命令 | 现有安全仲裁适配 |
| simulator / evaluator | 执行仿真、生成传感器；独立记录与评价 | 分层仿真后端与评价器 |

允许一个实现同时提供多个 role，但 manifest 必须列明输入、输出及角色占用，组合图不能重复分配同一控制职责。TEB/DWA 的 MBF controller 身份不能硬改成只输出轨迹的组件；用适配器保留其真实语义。

## 2. 标签与强约束分开

**标签用于检索，契约用于决定能否组合，证据用于决定能否宣称支持。** 三者分别保存。

推荐标签词表：

| 类别 | 示例 | 使用限制 |
| --- | --- | --- |
| 环境 | indoor、outdoor、flat、ramp、stairs_geometry、multilevel、underpass、dynamic_obstacles | 只能描述已声明的适用面，不能从名字推导能力 |
| 机器人 | ground、quadruped、differential、holonomic | quadruped 标签不代表含腿部控制器 |
| 空间表示 | planar、single_height、multisurface、voxel、mesh | 必须同时给地图 schema；不能用一个 3D 标签覆盖全部语义 |
| 资源 | cpu、gpu_optional、gpu_required | 具体依赖、显存、CPU/内存预算在强约束中明确 |
| 运行模式 | offline、simulation、real_robot | real_robot 不能由 simulation 自动晋级 |

能力证据记录独立字段：declared、contract_tested、simulation_verified、robot_verified。它们表示证据层次，不等于实验 PASS/FAIL/INVALID。每次晋级绑定组件版本、参数哈希、机器人模型、场景集合、运行模式和报告路径；同一算法在平层通过不自动获得 stairs_geometry 验证标记。

元数据缺失视为「尚不能判定兼容」并拒绝自动运行；与明确字段矛盾的「不兼容」分别提示。两者都不应被标成算法运行失败。

## 3. manifest 与组合锁定文件

每个组件 manifest 至少包含：

- 身份：schema_version、id、version、role、来源/许可证、适配器入口、代码版本与参数 schema。
- I/O：消息类型与 schema 版本、地图语义、维度、参考坐标系、单位、时间来源、数据新鲜度。
- 能力：运动学、支撑面假设、坡度/阶差/净空的适用约束、动态障碍与重规划支持、取消和反馈支持。
- 依赖：必需地图与传感器、外部库/运行环境、CPU/GPU 需求、启动前置、可选功能的实际开关。
- 所有权：发布的 TF 边、命令话题、ROS 名称空间、端口和设备占用，健康检查与停止方式。
- 证据：声明者、测试报告、版本范围与适用场景；无报告时只处于 declared。

示例片段仅展示 schema 方向，不是可运行组件，也不是已实现的 schema 文件：

```yaml
schema_version: 1
id: proposed.support_graph_astar
version: 0.1.0-design
roles: [global_planner]
tags: [ground, multilevel, cpu]
requires:
  map:
    schema: support_graph/v1
    occupancy_states: [free, occupied, unknown]
    multiple_surfaces_per_xy: true
  start_goal:
    schema: ground_goal/v1
    frame: map
    position_reference: support_surface
provides:
  route:
    schema: support_route/v1
    carries: [surface_id, map_revision, robot_profile_hash]
execution:
  cancellation: cooperative_with_process_watchdog
evidence:
  level: declared
  reports: []
```

schema 必须拒绝未知关键字段和错类型；版本不兼容时要求显式迁移，不能静默取缺省值。机器可读规格和样例在 V8-02/V8-04 交付，本计划不虚构已存在的文件。

组合锁定文件记录最终解析结果：组件及适配器精确版本/哈希、全部生效参数及来源、地图/场景/机器人模型哈希、传感器外参、TF 所有权、输入输出映射、依赖版本或容器摘要、随机种子、时钟模式、资源预算、评价器版本。敏感凭据不写入锁文件。运行前核对实物与锁文件，运行后不回改，任何变动生成新实验编号。

## 4. 核心数据契约

| 对象 | 必须表达的语义 | 不允许的隐式处理 |
| --- | --- | --- |
| RobotProfile | 机身/传感器包络、参考点、运动学、上/下台阶与坡度能力、制动能力、有效来源 | 把未经验证的数值当真实 Lite3 能力；用质点代替碰撞体 |
| SceneProfile | 地图范围、观测覆盖、支撑面/层间边、起终点、动态事件、物理或运动学载体 | 地图外、无点、零填充自动当自由空间 |
| PoseEstimate | frame、时间、位置/姿态、协方差或质量、重定位/失效状态、来源模式 | 真值伪装估计；TF 跳变后继续跟踪旧轨迹 |
| SupportMap | 地图版本、多个 surface_id、法向/净空/支撑、空闲/占据/未知、观测时间、连接约束 | 每个 XY 只取最高点后仍称多层地图；floor_id 代替连通性 |
| NavigationGoal | goal_id、frame、XYZ、目标参考点、目标支撑面/消歧规则、容差来源、请求时限 | 同 XY 不同层视为同目标；忽略 z、yaw 或状态恢复语义 |
| GlobalRoute | route_id、地图版本、机器人配置哈希、带支撑面身份的关键点、走廊、边类型 | 只交 nav_msgs/Path 而丢掉楼层、参考点与有效范围 |
| LocalTrajectory | trajectory_id、关联 route_id、时间参数、机体参考轨迹、动态约束与有效截止 | 将无时间路径当轨迹；旧地图轨迹无限沿用 |
| MotionCommand | 来源/租约、时间、有效期、目标控制接口、制动/停止语义 | 多节点直接发布最终 cmd_vel；取消后继续用最后一次速度 |

ROS1 可先保留标准消息作为载荷，以自定义消息/服务或配套元数据封装语义；具体消息定义在 V8-02 冻结。元数据必须与载荷同一 ID/版本，不能靠松散的两个话题「大概对应」。

### 4.1 坐标和高度

TF 边有唯一发布者，整棵树无环且每个 child 只有一个 parent。一般采用 map→odom→base 的职责分离，实际帧名从配置解析。外参、地图原点、地面高度与机体中心高度分别记录。SCAN mode3 的输入路径 z 与 body_height 相加行为必须被适配器精确处理，禁止两次补偿。

2D 组件可以消费显式投影后的状态，但转换记录必须写出丢失的信息、适用支撑面及有效范围。目标处于不同支撑层或楼层消歧失败时拒绝；跨层切换需明确连接与重新规划，不允许把整个三维路径直接压平交给 TEB。

### 4.2 时间和故障

记录 ROS 仿真时间与单调墙钟。运动/观测用仿真时间关联；进程超时、取消和仿真停钟监视用单调墙钟保护。若 planner 预算大于 harness 等待时限，启动前拒绝配置；harness 还须预留启动、反馈与取消时间，不能先超时再把未收齐结果归为算法 FAIL。

定位过期、TF 缺失、时间倒退、地图换版、传感器停更均产生独立事件。健康失效时停止推进目标、撤销轨迹并触发仲裁停车；恢复须重新校验版本与起点，不能自动续用旧轨迹。

## 5. 组合求解与拒绝原因

解析顺序：

1. 加载场景、机器人与 manifest；校验 schema/版本与必填字段。
2. 按角色解析依赖图，检测环、缺失角色、角色重复与资源冲突。
3. 比对地图类型、位姿维度、消息语义、控制接口和运动能力。
4. 选择明确登记的适配器；显示其信息损失与有效域，不擅自插入有损转换。
5. 校验 TF/命令唯一所有权、时钟、名称空间、运行环境、CPU/GPU 与停止链。
6. 生成确定性的展开配置、装配图、拒绝报告或锁定文件。

| 组合/事件 | 预期结论 | 必须给出的理由 |
| --- | --- | --- |
| 有效平面定位＋costmap＋GP/Navfn＋TEB/DWA＋仲裁 | 满足资源与接口条件后可启动 | 给出选中的组件、转换与职责图 |
| 6DoF 定位＋受限平面投影＋二维规划 | 条件兼容 | 必须指定支撑面与倾角/高度适用范围 |
| 多层支撑地图＋支撑图全局＋SCAN mode3 适配＋检查器 | 候选组合，须先通过专项契约测试 | 不从标签直接推断 SCAN 支持全部多层场景 |
| 三维路径直接接仅消费二维 costmap 的后端 | 拒绝 | 地图/路径语义不匹配，缺适配与适用域 |
| 两个里程计同时发布同一 odom→base | 拒绝 | TF 边所有权冲突 |
| SCAN 和 MBF 同时直写最终运动命令 | 拒绝 | 控制权冲突；只能发布带来源的建议给仲裁 |
| 标记 GPU 必需但当前环境无对应资源 | 拒绝 | 依赖与资源条件不满足 |
| 目标 XY 相同而 z/floor 不同且无法消歧 | 拒绝或要求补目标信息 | 目标支撑面不唯一，不能猜最近层 |
| 过期轨迹、缺地图版本、失去健康租约 | 运行期拒绝执行并停车 | 输出可定位的契约字段和事件编号 |

兼容结果采用「兼容／条件兼容／不兼容／信息不足」；实验结果仍用 PASS/FAIL/INVALID。生成了合法组合只代表满足静态条件，不证明运行一定成功。

## 6. 生命周期与任务 API

组件状态拟定为 discovered→configured→starting→ready→running→stopping→stopped，任何阶段可转 failed。ready 必须由可观测条件建立，例如地图可查询、TF 可用、数据新鲜；固定 sleep 不能代替就绪判断。

平台导航任务统一 goal、feedback、result、cancel。结果类型至少区分 SUCCEEDED、NO_PATH、BUDGET_EXCEEDED、CANCELED、INPUT_INVALID、COMPONENT_FAILED、SAFETY_STOP；每种结果有诊断字段，不能将所有失败映射成 timeout。组件异常退出、插件卡死由外部 watchdog 识别；取消不响应时，只终止属于该组合的进程组，独立仲裁停止命令。

启动按依赖顺序，失败回滚已启动组件，停止按依赖逆序。ROS1 的残留 master 注册、端口与进程必须清理并检查；不得杀掉同机其他任务。每轮实验使用可辨识的名称空间、端口/进程清单和资源锁。

真实设备适配器与仿真适配器分别注册，simulation 组合禁止解析到真实运动链。真实设备凭据和动作许可属于独立运行流程。

## 7. 实现与验证顺序

第一步只做有限组件集和有限规则，证明能拒绝真实不兼容例；不先写泛化插件商城。第二步让旧 2D 栈走完整注册/校验/运行链。第三步接入多层表征与 SCAN 候选，确保 2D/3D 共用任务和证据合同。最后再增加算法数量和界面。

契约验证采用正负对照：合法组合运行、缺字段与错版本拒绝、TF 重复发布拒绝、时钟/传感器故障停车、取消和崩溃清理、同配置生成同锁文件。任务实现及验收 ID 见 [23](23_v8任务队列.md)，场景与判读规则见 [24](24_仿真验收与迁移方案.md)。
