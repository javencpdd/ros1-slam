## 坑16 · `kill -0` 判进程存活在 root 属主进程上返回 EPERM → 误判「进程已死」；`ss -lntp` 不含 UDP → 假报「未监听」（登记日 2026-10-08 · 源于主理人实测踩坑，小王登记 · 验收/核验类作业单通用规范）
- 症状：红线核验（确认 root 侧 foxy 生产栈未被触碰）时用 `kill -0 <pid>` 探活，对 root 属主进程 **115792 / 115795 / 115797 / 115799** 全部失败 → 被读成「进程不存在」，一度误报为「**生产栈被杀**」重大事故；另一次用 `ss -lntp` 查 UDP 43897（qnx2ros，02 坑5 同族）返回空 → 误报「端口未监听」。
- 根因：两条都是**工具语义误用**，非现场状态异常。① `kill -0` 只做信号发送权限检查：进程存在但属主不同且无 CAP_KILL → 返回 **EPERM（Operation not permitted）** 而非 ESRCH（No such process）；沙箱身份 ros1-slam 对 root 进程恒得 EPERM，`$?≠0` 被当作「死」。② `ss -lntp` 的 `-t` 限定 TCP，UDP socket 天然不列（`-n` 数字化、`-p` 需 root 才显示进程名）→ 空输出 ≠ 未监听。
- 处置（固化为**验收/核验类作业单通用规范**，建议后续 Gate 模板补这行）：
  - **进程存活/属主核验一律用** `ps -o pid,user,lstart,etime,args -p <pid1>,<pid2>,...`（能看到属主与启动时刻，兼作「生产栈未被重启」的承重证据）或 `pgrep -a <name>`；**禁止用 `kill -0` 作存活判据**（尤其跨属主场景）。
  - **端口归属核验**：TCP 用 `ss -lntp`，**UDP 必须用 `ss -ulnp`**（qnx2ros/43897、Livox 56300/56301/56400/56401 皆 UDP）；需进程名时加 sudo 或以 `lsof -nP -iUDP <port>` 复核，零权限则只报端口在位、不臆断属主。
  - 本次实际后果：**零生产栈损伤**，纯误报；已按「先 ps/pgrep 复核再下结论」补进核验动作口径。**小王 2026-10-08 只读复核（零节点、零改动）**：`ps -o pid,user,lstart,etime -p 115792,115795,115797,115799` → 四件 `user=root`、STARTED `Mon Oct 5 01:27:51/53 2026`、ELAPSED `2-23:30+`（**在位且未重启**）；对同四 PID `kill -0` 逐条返回 `kill: (PID) - Operation not permitted` = **EPERM 实证**（非 ESRCH），与本坑根因判定一致。
- 计划书是否需要更新：不需要改正文；建议 P0.5 双查/Gate 作业单模板增补一行「探活禁 `kill -0`，用 `ps -o pid,user,lstart` 或 `pgrep -a`；UDP 归属查 `ss -ulnp`」（由主理人决定是否入 v4.x 补丁）。

## 坑17 · Edit/写入工具走 temp+rename 会冲掉已补的 ACL；ysc 落盘致属主漂移（登记日 2026-10-08 · 源于 G7-① 补验收与 SCAN 拷包 · 主理人登记）

- 根因：① 团队规范假定「沙箱属主文件写入切 `sudo -u ros1-slam`」，但本机 **ysc 的 sudo 需要密码且 ysc 不在 ros1-slam 组**，该通道在无人值守批处理下不可用；② rename 覆盖 = 新 inode，显式 ACL 不随内容迁移。
- 处置（**无 sudo 可用路径**，本轮实测有效）：

  - **`setfacl` 必须是编辑动作的一部分，不能只在首次建文件时做一次**——这是本坑的核心教训。

  - 核验类命令一律 `stat -c '%U:%G'` + `getfacl -p`，**不要用 `kill -0` 那类依赖属主的探测**（见坑16）。
- 计划书是否需要更新：建议 v4.x 在「程序运行身份与环境规范」第 1 条后补一行——「无人值守批（无交互 sudo）下：ysc 落盘 + 每次编辑后 setfacl 补 `u:ros1-slam:rwx`；git 由 ysc 跑但身份取自 repo config」；不改 G0–G9 判据原文。登记人：主理人（Qoder 第三会话，2026-10-08）

## 坑18 · 未加引号的 heredoc 会把正文里的 markdown 反引号当命令执行（登记日 2026-10-08 · 源于 SCAN 集成收尾落账事故 · 主理人登记）

## 坑20 · 后台批启动的两则操作坑（登记日 2026-10-08 · 源于 M2R4/M2R5 批次 · 主理人登记）
- 症状一：以「nohup bash driver.sh > /tmp/out/driver.log 2>&1 &」启动，脚本内部才 mkdir 该目录 —— 重定向发生在脚本运行**之前**，目录不存在即失败，任务根本没起跑，而前台只显示"无输出"。本轮实跑浪费了一次起跑判断。
- 处置一：**启动命令里先 mkdir -p，再重定向**；或让驱动脚本自身打印起跑行到已存在的目录。任何"批没动静"的排查顺序第一位看的是驱动日志文件是否存在，而不是进程列表。
- 症状二：以 setsid + & 后台化后，前台 SSH 命令仍会因管道未关而报「命令执行超时」（exit 124），但后台任务其实**已在正常运行**。把工具超时误读为任务失败会导致重复起跑、争用同一隔离端口。
- 处置二：后台化一律配 「> 日志文件 2>&1 < /dev/null」；判定起跑以「日志文件出现 + pgrep 命中」两件为准，不看那次 SSH 调用的返回码。

## 坑21 · Gazebo 把 fixed 关节树合并成单一 body，body 名 = URDF root link 名（登记日 2026-10-08 · 源于 M2R5/U1 改 root 的前后对照 · 小明的实测、主理人登记）
- 症状/事实：同一 xacro 只把固定关节 torso_to_base 反挂为 base_to_torso（parent/child 互换、origin 恒等不动），/gazebo/get_model_properties 的 body_names 即由 「TORSO」整族变为 「base_link」；GetLinkProperties 查另一个 link 名一律回「link not found, did you forget to scope the link by link name」。⇒ **仿真里的物理 body 只有一个，名字跟着 root link 走**，URDF 的其余 fixed 子帧不是独立 body。
- 为什么这是个坑：凡以「link 名」为锚的外设配置（gazebo reference=某 link、摩擦/传感器挂载、get_link_properties 类校验、下游按 body 名取量的脚本）在 root 变更后**语义指向会变**；反过来说，把 root 从机体帧改成契约帧时，这类引用必须逐一过一遍，不能只核 TF 树。
- 本轮实测的等价面（改前/改后各一台，同一探针 m2_v6_probe.py）：落地高度 z 的 min/max/span 全等（0.109869 / 0.150000 / 0.040131），mean 差 3.5e-5（采样窗抖动量级），姿态四元数单位、x/y 恒 0。⇒ 「改 root 只动拓扑、不动物理」在**静止与接触面**上是核出来的，不是断言的。
- 处置（入验收作业单）：凡动 URDF root / 固定关节方向，回归判据里必须包含 ① get_model_properties 的 body_names/canonical/joint_names/geom_names 前后对照；② 落地 z 与姿态前后对照；③ 物理行为判据（stageA 漂移/回程）重取；④ 按 body/link 名取量的脚本先确认可用性。
